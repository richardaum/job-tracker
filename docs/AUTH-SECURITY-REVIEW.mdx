# Authentication Security Review

Authentication architecture review — updated 2026-08-22.

## Architecture

```
Browser → Better Auth `/api/auth/sign-in/social`
  → Google OAuth 2.0 → `/api/auth/callback/google`
  → opaque Better Auth session cookie

GraphQL → SessionAuthGuard → Better Auth session lookup → active domain user
```

Better Auth owns OAuth state, provider accounts, sessions, session renewal, and
session revocation on sign-out. The domain `users` table retains authorization
data (`role` and `status`) and is deliberately separate from Better Auth's
`user` table. Both rows share the same UUID.

`UserType.authProviders` is derived from Better Auth's `account.providerId`;
the API does not expose a legacy account entity.

## Cookie and origin policy

- Local (`localhost:3100` → `localhost:3101`): `SameSite=Lax`, no `Secure`.
- Current production topology (Vercel web → DigitalOcean API): `SameSite=None;
  Secure`, because the origins are cross-site.
- `trustedOrigins` explicitly allows `WEB_URL`; do not disable Better Auth's
  CSRF or origin checks.
- A future `api.newjobtracker.app` topology can use host-only or shared
  same-site cookies, but is not required for the current deployment.

## Operational requirements

1. `BETTER_AUTH_SECRET` must be a stable, random value of at least 32
   characters. Do not rotate it during an OAuth flow or without a migration
   plan for active sessions.
2. `BETTER_AUTH_BASE_URL` must be the public API origin for that environment.
3. Google must allow `${BETTER_AUTH_BASE_URL}/api/auth/callback/google` as an
   authorized redirect URI.
4. Run the Better Auth migration before deploying code that reads sessions.

## Domain authorization

`SessionAuthGuard` accepts only a valid Better Auth session whose matching
domain user is active. `RolesGuard` continues to enforce domain roles. The
development bypass is disabled in production.

## Migration note

The migration copies existing Google identities into Better Auth's `user` and
`account` tables, creates the `session` and `verification` tables, and then
removes the custom JWT/JTI columns and `user_accounts` table. Existing custom
JWT cookies do not survive this migration; users sign in again once after the
deploy.
