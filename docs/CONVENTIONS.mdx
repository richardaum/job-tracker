# Conventions

Guidelines for **application and package code**, **LeanSpec** (`specs/`), and Storybook (**Documentation → Project**, **Conventions**, **Specs**). Product overview: **[PROJECT.mdx](./PROJECT.mdx)**.

## Documentation MDX (`docs/`)

- **Language**: All **documentation** in this repository is written in **English** — including `docs/**/*.mdx`, LeanSpec under `specs/`, root and package **README** files, Storybook documentation (this page and related MDX), agent skills, and other in-repo technical prose. User-facing UI strings may follow product or localization decisions separately; the documentation layer stays English for a single shared baseline.
- **Format**: All files under `docs/` are **`.mdx`**. Do not add plain Markdown (`.md`) here — MDX is required so Storybook picks them up (`packages/ui/.storybook/main.ts` includes `docs/**/*.mdx`) and tooling stays consistent.
- **LeanSpec in Storybook (`docs/specs/`)**: **`docs/specs/*.mdx`** is **generated** from `specs/**` markdown (`README.md`, `HISTORY.md`, `INDEX.md`, and each numbered spec’s `README.md`) so the sidebar shows the same content as LeanSpec with the same Markdown rendering as other docs pages. Output is **gitignored**; it is written before **`pnpm --filter @job-tracker/ui run dev`** / **`build-storybook`** (see **`packages/ui`** `sync-specs-docs`) and by **`pnpm storybook:sync-specs`** at the repo root. Under **PM2** (`ecosystem.config.cjs`), the **storybook** app watches **`specs/`** and the generator script so restarts refresh docs. Do not edit generated files by hand.
- **No `---` before headings**: Do not place a thematic break (`---`, horizontal rule) on the line directly above any Markdown heading (`#` through `######`). It adds noise in Storybook and weakens heading hierarchy visually. Use blank lines only, or restructure sections (lists, paragraphs) instead of separating with a rule right before a title.

- **Uppercase `*.md` / `*.mdx` stems (repository-wide)**: The filename **before** `.md` or `.mdx` must use **uppercase ASCII letters** (hyphens between segments are fine; **no lowercase** in the basename). Examples: **`README.md`**, **`PROJECT.mdx`**, **`COSTS.mdx`**. **Exceptions:** (1) slash-command sources under **`.ai/commands/`** use **lowercase** basenames (e.g. **`commit.md`**) so they match **`/commit`** invocations in editors; (2) generated **`docs/specs/<NNN-slug>.mdx`** use the same **lowercase kebab-case** stem as the matching **`specs/<NNN-slug>/`** folder. When renaming, update links, scripts, globs, and agent skills that reference the path.

## LeanSpec (`specs/`)

Numbered folders: `specs/<NNN-slug>/` with primary **`README.md`** (optional companions at spec root too). Chronicle: **`specs/HISTORY.md`** next to **`specs/README.md`**, linked from **`008-docs-history`**. Overview: **`specs/README.md`**. Config: **`.lean-spec/config.json`**.

### Source of truth and alignment with code

- The primary **`README.md`** for a numbered spec is the **source of truth** for what that scope commits to: requirements, outcomes, and high-level design (flows, boundaries, ownership).
- **High-level alignment is mandatory:** when implementation adds, removes, or changes that committed story, **update the spec in the same change set** so docs and code stay aligned. **Code and tests** remain authoritative for line-by-line behavior; the spec does not need to mirror every file, but it **must not** drift into contradiction with shipped intent that guides product or engineering decisions.

### Structure bands (this repository)

| Range             | Role                                                                   |
| ----------------- | ---------------------------------------------------------------------- |
| `001-*` … `006-*` | Archived earlier-phase snapshots (`status: archived` in frontmatter).  |
| `007-*` … `011-*` | **`docs-*`** governance: definition, history, project, roadmap, state. |
| `012-*` … `026-*` | Active **product** and **technical** scopes for current work.          |

### Naming and prose

- Directory slugs under `specs/`: lowercase **kebab-case**.
- **One primary outcome** per spec; keep terminology aligned across roadmap, project, product, and technical docs.

### Traceability IDs (`[P-XXX]`, `[T-XXX]`, …)

- **Always attach stable bracketed IDs** to anything that other specs, history, or roadmap entries should cite: product-facing bullets and outcomes use **`[P-NNN]`**; technical work items use **`[T-NNN]`**; also **`[R-NNN]`** (roadmap), **`[H-NNN]`** (history entries), and other prefixes already used in **`specs/HISTORY.md`** and active product READMEs.
- **Reuse the same ID** across `specs/`, `docs-roadmap`, `docs-history`, and cross-spec references—do not rephrase the same requirement under a new number.
- When splitting or superseding scope, **record the mapping** in history (which `[P-XXX]` / `[T-XXX]` moved or replaced) so grep and changelog lines stay unambiguous.
- **Application and package source (outside LeanSpec Markdown):** Do not embed traceability tokens (`[P-NNN]`, `[T-NNN]`, `[D-NNN]`, …) in executable code—no string literals, identifiers, user-visible copy, or logs that carry those IDs. **Comments** may cite a token **only** alongside a **very short** explanatory phrase (what behavior, boundary, or spec scope the note refers to); bare ID lists or parenthetical IDs without that context are not allowed. Exempt: tooling and tests whose purpose is to parse, link, or exemplify those tokens (e.g. Storybook spec markdown helpers and their fixtures).

### Workflow

- Prefer **`pnpm exec lean-spec`** for `create`, `update`, `validate`, `board`, and **`rel`** (dependencies), not only ad-hoc tree edits.
- Meaningful increments: update **`docs-roadmap`**, **`docs-state`**, and **`docs-history`** (prepend to **`specs/HISTORY.md`**).
- When new requirements or acceptance criteria arise for scope already owned by a numbered spec (**`specs/<NNN-slug>/README.md`**), **update that spec** in the same change set (stable **`[P-NNN]`** / **`[T-NNN]`** IDs per **Traceability IDs** above), then **`pnpm leanspec:sync-spec-indices`** when references or metadata change. See **Source of truth and alignment with code** above.
- Merge-ready: code and tests green; **`pnpm leanspec:validate`** (CI and pre-commit).

### Spec indices (`specs/`)

- **`specs/README.md`** only **links** to **`specs/INDEX.md`** — no embedded grids.
- **`specs/INDEX.md`** (generated) — minimal **YAML frontmatter** only: **`specCount`** (numbered folders with **`README.md`**), **`requirementIdCount`** (distinct bracket IDs **`[P-NNN]`**, **`[T-NNN]`**, … scanned from **`specs/`** Markdown, excluding **`specs/README.md`** and **`specs/INDEX.md`**), and **`historyCount`** (list lines `- [H-NNN]` in **`specs/HISTORY.md`**). Also **`formatVersion`** and **`generator`** — no timestamps so **`--check`** stays deterministic. No embedded **`specs`** or **`refs`** lists in the file.
- **Mandatory:** after **creating** a new numbered spec folder, editing **`status:`** or the primary **`#`** title, or **adding or editing** any **`[P-NNN]`** / **`[T-NNN]`** (etc.) reference in LeanSpec Markdown under **`specs/`**, run **`pnpm leanspec:sync-spec-indices`** in the same change set. Do **not** hand-edit **`specs/INDEX.md`** — regenerate with the script.
- CI and **`pnpm ci:local`** run **`pnpm leanspec:sync-spec-indices -- --check`** so a stale **`specs/INDEX.md`** fails the gate. **`specs/INDEX.md`** is listed in **`.prettierignore`** so Prettier leaves generated YAML intact.

## Repository architecture

- **`apps/web`**: UI only. **`apps/api`**: backend API. Do not add API routes or server actions in web.
- OpenAI: use an internal API facade, not direct frontend calls.
- Cross-package imports: workspace aliases where configured (`@api/*`, `@ui/*`, `@/*`).
- Within an app's **`src/`**, prefer **absolute imports via the app's root alias** (e.g. `@/module/file` → `src/module/file` in `apps/web` and `apps/extension`) instead of **`../`** parent chains. Same-directory **`./`** imports are fine for co-located files.
- Environment: typed env modules only — no raw `process.env` in application code.

### NestJS modules and guards

- **AuthModule dependency:** Any NestJS module that defines resolvers decorated with **`@UseGuards(JwtAuthGuard, RolesGuard)`** (or similar guards) **must import `AuthModule`**. Guards like `RolesGuard` depend on `Reflector` and `UserService` which are provided through `AuthModule`. Omitting this import causes `UnknownDependenciesException` at startup.
- **Import pattern:** Add `AuthModule` to the module's `imports` array, matching the pattern used by `CompaniesModule`, `ApplicationModule`, and other authenticated domains.

### Async task JSONB metadata (`fieldMetadata`)

Fields named `{action}Metadata` (e.g. `summaryMetadata`, `conversionMetadata`, `generationMetadata`) are JSONB columns carrying `AsyncMetadata` (`{ status, error?, generatedAt? }`). They pair with a sibling data column (`summary`, `conversionResult`, etc.) that holds the **output** once the async task completes. The metadata tracks **processing state only** — never inline business data inside it.

| Rule | Detail |
|------|--------|
| **`null` semantics** | `metadata IS NULL` means the async task was **never requested** for that record. The sibling data column must also be `NULL`. |
| **`NOT NULL` pairing** | If the data column is `NOT NULL` (output exists), the metadata column **must NOT be `NULL`** — its `status` should be `COMPLETED` and `generatedAt` must be set. Conversely, `metadata.status = COMPLETED` implies the data column is populated. |
| **Backfill coverage** | Migrations that create the metadata JSONB from legacy columns or fix stale state must handle **both** cases: (a) metadata exists with `generatedAt IS NULL`, and (b) data column populated but metadata still `NULL`. |
| **Atomic updates** | Background workers use `QueryBuilder` with JSONB `||` operator (merge) and optimistic concurrency (`WHERE metadata->>'status' = expectedStatus`). |
| **Stale recovery** | Services implement `OnModuleInit` to reset lingering `PROCESSING` records to `FAILED` on startup. |
| **Canonical spec** | `specs/034-technical-async-task-pattern/PATTERN.md` — full type definitions, entity mapping, service pattern, and frontend display. |

When touching any `{action}` data field, verify its `{action}Metadata` consistency. When expanding async task slots (fit analysis, draft conversion), follow the same `{action}Metadata` naming.

## Web view models

GraphQL screens should keep **rendering thin**: put API-to-display shaping (derived lists, formatted fields, empty/loading/error flags, props from query results) in **view-model hooks**, not large page or panel components.

| Topic              | Rule                                                                                                                                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Naming**         | `useApplicationDetailsViewModel`, `useCompaniesListViewModel`, etc. (`use<Feature><Screen>ViewModel` or feature-scoped names like `useNotesPanelViewModel`).                                                    |
| **Location**       | `apps/web/src/modules/<domain>/<area>/hooks/use<Name>ViewModel.ts` (consistent within a module).                                                                                                                |
| **Return**         | One object with named fields. Avoid exposing raw `data` unless mutations still need it. Pure formatters live in `utils/` or `*.shared.ts`; the hook **calls** them.                                             |
| **Queries**        | Prefer generated hooks from **`@/gql/hooks`** over Apollo **`useQuery(Document)`** / **`useMutation(Document)`** (see **GraphQL client** below). `skip`, variables, and result handling live in the view-model hook (or a thin `useXxxQueries`). UI-only state (modals, drafts, scroll keys) may stay on the page or in `useXxxUiState` when that clarifies boundaries. |
| **Dependencies**   | Apollo and pure helpers allowed; **must not** import from `app/` (`app → modules` only).                                                                                                                        |
| **Types**          | Prefer generated GraphQL types; avoid `any`.                                                                                                                                                                    |
| **React 19/Compiler** | Follow **React 19 and React Compiler** below (prefer plain derivations; avoid default memoization; refs as props).                                                                                           |
| **Size**           | Split large hooks by concern; place new hooks where reuse and call sites stay clear.                                                                                                                            |

### GraphQL client (`apps/web`)

- Prefer **generated** query and mutation hooks from **`@/gql/hooks`** (e.g. `useApplicationsQuery`, `useCreateApplicationMutation`) over calling Apollo Client **`useQuery`**, **`useMutation`**, or **`useLazyQuery`** with a **document** argument (e.g. `useQuery(SomeDocument)`). Codegen keeps operations, variables, and result types aligned with **`apps/api/src/schema.gql`**.

Full technical notes: `specs/022-technical-view-model-web-layer/README.md`.

## TypeScript and React

- **Imports**: Prefer **`@/…`** (or the package’s configured alias to `src/`) over **`../`** traversals. Avoid inline type-only imports like `Foo<import("@/path").Bar>`. Use a top-of-file `import type { Bar } from "@/path"` (or `import { type Bar }`) and `Foo<Bar>`. Inline `import("...")` types are harder to read, grep, and refactor.
- **Async errors**: Prefer **`tryRun(...)`** from **`@job-tracker/try-run`** for promise error handling (`const [error, data] = await tryRun(promise)`; synchronous work can use `tryRun(() => …)` without `await`) instead of wrapping async flows in `try/catch` when behavior is equivalent. Keep `try/catch` where language-level control flow is required (for example, `finally`, synchronous exceptions, or framework boundaries that rely on thrown errors in a specific block).
- **Reexports**: Avoid files that only forward symbols (`export { x } from './x'`, barrels created just to shorten paths). Import from the module that declares the export so jumps, refactors, and tooling stay truthful. **Exception:** deliberate **public entrypoints** — e.g. a workspace package **`index.ts`**, or a module boundary documented as the stable façade for that slice.
- **Named types**: Prefer a top-level `type` or `interface` over inline anonymous shapes in parameters, props, return types, and generic arguments when the object or union is non-trivial or reused. Keeps signatures readable and searchable. Fine to keep primitives, simple utilities (`Record<string, string>`), or one-off literals inline when a name adds no clarity.

### Nova convention

- **Module-level regular functions**: **`function`** declarations at module scope (helpers, parsers, predicates, small pure utilities—not nested inside another function or class) belong in the **lower part** of the file: **below** imports, top-level types, constants, and the primary exported surface (React components/hooks, classes, schemas, routes, etc.). Excludes nested functions and class/object methods.

## React 19 and React Compiler

- **Memoization defaults**: Avoid unnecessary `useMemo` and `useCallback`. Prefer plain `const` derivations and direct closures; add memoization only for expensive work, a documented reference-stability contract, or a lint/compiler requirement.
- **Refs**: Do not use `forwardRef`. Pass `ref` as a normal prop; UI components use `ref?: React.Ref<T>` on the props type and attach it to the underlying element. ESLint blocks `forwardRef` / `React.forwardRef` in `apps/web` and `packages/ui`.

## UI: composition, layout, and components

### Composition and hydration

- **`asChild`** (`@radix-ui/react-slot`) for interactive UI (e.g. `button`, `a`) when wrapping other interactives or `NextLink` — avoids invalid nesting (`<button>` in `<button>`) and hydration errors.
- Do not mix block and inline in sibling slots; use the same display type across equivalent slots so height and alignment stay consistent.

### Buttons

- Use `state` (`"default" | "loading"`), not a boolean `loading` prop. Loading disables the control and sets a11y attributes.

### Dialogs and confirmations

- **`Dialog`**: flex layout — use `childrenClassName="flex flex-col"` and `flex-1 min-h-0` on children that should fill height and scroll internally (e.g. `NotesPanel`).
- **`ConfirmDialog`** (`@job-tracker/ui`) for confirmations, especially destructive actions — not `window.confirm` / `alert` / `prompt` in app code.
- Prefer small feature components wrapping `ConfirmDialog` over duplicating cancel + confirm footers.
- Storybook: **Components → ConfirmDialog** (`pnpm --filter @job-tracker/ui storybook`).

### FieldWithLabelAction Tooltips

- When a tooltip is required within the `content` (body) of a **`FieldWithLabelAction`**, always use the **`FieldWithLabelAction.Tooltip`** compound component. This ensures consistent positioning (defaulting to `side="bottom"`) and maintains the compound component pattern established for this control.

### Editors (TipTap)

- Use **`autofocus`** in composers and edit dialogs; `autofocus="end"` when editing existing content (cursor at end).

### List and detail page layout

Screens that pair an **index list** with an **item detail** route (same product area) should follow one coherent shell. Canonical reference: **`/applications`** and **`/applications/[id]`** (`ApplicationsPage`, `ApplicationDetailsPage`).

#### List (index)

- **Primary “New” action**: Place creation (or equivalent primary entry) in the **top tool row** of the list view, not inside the scrollable card stack. From **`sm`** upward, lay out that row as a horizontal band with **`justify-between`**: list-level controls (search, filters, scope hints) on the **start** side, the primary button or split button on the **end** (`sm:w-auto` on the actions cluster so it does not stretch full width). On smaller viewports, stack the row with a consistent vertical gap.
- **List body**: Render entities as a **vertical stack of cards** (`Stack` with a small gap, e.g. `gap="sm"`), in a **`flex-1 overflow-auto`** (or equivalent) region so the tool row stays pinned and the list scrolls.
- **Card component**: Implement **one card component per entity type in its own file** (e.g. `ApplicationCard.tsx`). The page imports and maps over data; it should not inline large card markup.
- **Title and actions on each card**: On the **first row** of a card, group the **entity title** (link to detail when applicable) and **inline actions** (status, icon buttons, overflow menus) in a **single flex row** with **`items-center`** and a **tight gap** (e.g. `gap-2`). Do not separate title and actions with a large vertical spacer or a second “toolbar” strip— they read as one header line. Secondary metadata (company, dates, tags) belongs on following rows.

#### Detail (item)

- **Header**: The detail shell has a **title** at the top (`Heading` or equivalent) and a compact **Actions** control (e.g. `Button` + `DropdownMenu` labeled “Actions” for destructive or secondary operations). Pages may add a **back** link row above the title; keep the actions control **aligned with that top band** (e.g. back on one side, Actions on the other) so the title block stays uncluttered. Loading, error, and empty states stay in the content area below the header.
- **Main and optional side column**: **Primary content** lives in the **main column** (left in LTR). **Optional supplementary UI** (activity, chat, timeline— **not** the primary form) may sit in a **secondary column** to the right on wide layouts. Use a **CSS Grid** with a fixed or max width for the side column (e.g. `lg:grid-cols-[minmax(0,1fr)_360px]`), **`min-h-0`** on both tracks, and **`overflow`** / **`border-l`** on the side panel so nested scroll regions work.
- **Responsive integration**: Below the **`lg`** (or chosen) breakpoint, **collapse to one column**: fold the side column into the same flow as the main column—typically by **adding its content as extra tabs** on the same `TabsList` so nothing is only reachable on desktop. The reference detail page uses **one tab strip** on small screens (overview, description, notes, history) and **splits** overview/description tabs from the activity side panel on **`lg+`**.
- **Tabs (optional)**: When the main area has multiple subviews (e.g. overview vs. long-form body), use **`Tabs`** for the **main column** first. Add more triggers only when the side column is merged for small breakpoints, so navigation stays consistent.

## Web application patterns

- **Controllable state**: `apps/web/src/modules/applications/shared/hooks/useControllableState.ts` when a component supports controlled (`value` + `onChange`) and uncontrolled (`defaultValue`) modes.
- **Dialogs**: Implement in dedicated files, not inline in page/panel components — clearer context and reuse.
- **`TipTapEditor` / `aiActions`**: Prefer an inline literal array in props (e.g. `aiActions={[actionA, actionB]}`) over a `const` used only for that prop.
- **Other logic**: For non–screen-level behavior, use a dedicated hook or pure function in its own file when scope is clear (see **Web view models** for GraphQL screens).

### New implementation extraction M.O.

When introducing or refactoring a feature, use this extraction-oriented Modus Operandi to keep implementation scalable and testable across domains.

- **Choose extraction granularity intentionally:** pick one or combine multiple levels based on file complexity and reuse potential:
  - **Contextual (coarse):** isolate vertical slices and domain boundaries.
  - **Functional (medium):** extract orchestration into hooks/services and separate domain logic from rendering.
  - **Atomic (fine):** extract pure utilities and business-agnostic primitives.
- **Group by context, not technical bucket:** co-locate components, hooks, and types in the feature/domain area instead of generic global folders (`/hooks`, `/utils`) when scope is local.
- **Prefer low coupling:** remove hidden global dependencies where practical; use dependency injection and generic typing (`<T>`) when that improves reuse or testing.
- **Apply SRP pragmatically:** each extracted unit has one clear responsibility and high cohesion, but avoid abstraction that does not reduce cognitive load or improve testability.
- **Keep orchestration and primitives separate:** high-level modules express declarative business flow; low-level modules stay infrastructure-oriented and domain-agnostic.

Before finalizing an extraction, document or validate these points in the PR/spec context:

- **Name + contract:** clear exported name and TypeScript signature.
- **Rationale:** why extraction improves maintainability, readability, or testability for this feature.
- **Level classification:** whether the module is high-level (domain orchestration/rules) or low-level (utilities/infrastructure) and why.

## GraphQL list consistency

For delete mutations on list-backed entities in `apps/web`, prefer cache-first list consistency with **`removeDeletedEntityFromListCache`** from `apps/web/src/modules/applications/shared/utils/apolloDeleteCache.ts` instead of defaulting to `refetchQueries`.

- In the mutation `update(cache, { data })`, call `removeDeletedEntityFromListCache(cache, { mutationData: data, mutation: DeleteXDocument, query: ListXDocument })`.
- Pass generated GraphQL documents from `@/gql/hooks` (`DeleteXDocument` + list query document). Do not hardcode list field names, typenames, or manual `deletedId` parsing in the component.
- Keep refetch as a fallback only when list consistency depends on server-side derivations that the local cache update cannot represent safely.

### Delete mutations payload standard

- Do not model delete mutations as bare **`Boolean`** returns.
- For delete-by-id operations, return a payload object with at least:
  - **`success: Boolean!`**
  - **`deletedId: ID!`**
- Keep mutation names explicit (`deleteApplication`, `deleteCompany`, etc.) and use the payload in client operations to preserve a typed, extensible contract.
- When expanding behavior later (soft delete metadata, cascade stats, audit IDs), extend the payload object instead of changing a scalar contract.

## Agent skill: `job-tracker-api` (GraphQL)

The skill **`.ai/skills/job-tracker-api/SKILL.md`** is the **canonical** copy in this repo. **`pnpm setup-ai`** mirrors **`.ai/skills`** into **`.cursor/skills`**, **`.claude/skills`**, **`.agents/skills`**, and **`.gemini/skills`** (see **`scripts/setup-ai-symlinks.mjs`**). Edit only under **`.ai/skills`**, not the mirror trees.

**Keep the skill aligned with the live GraphQL contract whenever application-related API capabilities change.**

- **Source of truth for types and operations:** **`apps/api/src/schema.gql`** (generated; do not hand-edit the schema file to “fix” docs — change resolvers/entities and regenerate).
- **Update the skill in the same change set** as the API change when practical (or in an immediate follow-up PR) so agents and humans are not guided by stale operation names, inputs, enums, field lists, or behavior notes.
- **Typical triggers:** new or removed queries/mutations/types, renamed fields, `CreateApplicationInput` / `UpdateApplicationInput` / related input shapes, enum members, validation or merge rules (e.g. compensation), auth or error behavior that the skill documents, and any narrative that quotes the schema (tables, examples, command-to-operation mapping).
- **What to refresh in `SKILL.md`:** the frontmatter `description` if scope changes; operation inventories; input/field lists; examples and cross-references to resolver or util files when those rules move; pitfalls that contradict the previous schema.

If the schema changed for **`apps/web`**, run **`pnpm --filter @job-tracker/web run codegen`** as usual — the skill is documentation for agents alongside that generated client, not a replacement for codegen.

## Development: mobile debug (Cursor)

When debugging web from a phone (e.g. via ngrok), do not point the client at `127.0.0.1` for debug ingestion — mobile cannot reach host loopback; HTTPS may block mixed content.

Use a same-origin dev route in `apps/web` (e.g. `"/__debug_ingest"`) proxied/rewritten by Next.js in development only. Derive the target from allowlisted env vars, not hardcoded production behavior. Disable ingestion when the destination cannot be resolved.

## Quality gates

- **Lint and Prettier (human or AI)**: When ESLint or Prettier reports an issue, **fix it via the project CLI first** — for example root or package **`pnpm lint`** (with autofix where configured), **`eslint --fix`**, or **`prettier --write`** on the affected files or scopes. Prefer that over hand-editing many lines in an editor or chat: the tools apply consistent, repo-configured rules and use fewer tokens than manual patch-by-patch fixes.
- Lint, format, and typecheck before merge-ready changes.
- Run unit/integration, e2e, and Storybook tests for impacted layers.
- Keep CI coverage thresholds and story coverage for exported UI components.
- After config changes, validate env schemas and runtime boot paths.
