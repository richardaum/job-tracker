# ADR-004: Three Orchestrator Services for Jobs Domain

## Status

Accepted — **Implemented (manual, 2026-05-24)**

## Date

2026-05-24

## Context

Commit `a2f4f493` split a monolithic `JobsRepository` into focused classes, including `JobAsyncMetadataRepository` (CAS on `fillMetadata` / `summaryMetadata`) and `JobFillPersistence` (transactional fill finalize). That improved separation but left fill and summary logic scattered across misnamed helpers and a bloated `JobsService`.

Before wiring `autoFillEnabled` on draft create, the domain needed a clear orchestration model aligned with `backend/layer-repository.md`: **services orchestrate**, **repositories stay thin CRUD**.

## Decision

Replace the fill-persistence + async-metadata split with **three orchestrator services** and thin repository metadata helpers:

1. **`JobsService`** — job lifecycle orchestrator: CRUD, stage events, company/salary/tag resolution, domain events (`JobCreated`, `JobUpdated`). Does **not** own fill or summary workflows.

2. **`JobAutomaticFillService`** — all automatic fill:
   - `fillJobAutomatically()` — start fill (PROCESSING + `FillJobRequested`)
   - `processFillJob()` — AI extract, normalize, transactional finalize, complete/fail metadata
   - Stale fill recovery on module init via `JobsRepository.resetStaleFillProcessing()`

3. **`JobSummaryService`** — all summary (renamed from `SummaryService`):
   - `requestSummary()` / `requestSummarySync()` — queue or inline generation
   - `doGenerate()` — AI generation worker
   - Stale summary recovery via `JobsRepository.resetStaleSummaryProcessing()`

4. **`JobsRepository`** — thin CRUD plus conditional JSONB metadata methods:
   - `updateFillMetadataIfStatus`, `updateSummaryMetadataIfStatus`
   - `beginFillAutomaticallyProcessing`, `resetStaleFillProcessing`, `resetStaleSummaryProcessing`
   - Shared SQL in `apps/api/src/domains/shared/async-metadata.helper.ts`

5. **Listeners remain thin** — `FillJobEventListener` → `JobAutomaticFillService.processFillJob`; `SummaryEventListener` → `JobSummaryService` (+ settings gate).

6. **Delete** `JobFillPersistence`, `JobAsyncMetadataRepository`, and `summary.service.ts`.

### Orchestration layers

```
JobsService                    ← lifecycle (create, update, delete, stages)
JobAutomaticFillService        ← fill workflow + TX finalize
  ├─ JobsRepository            ← CRUD + fill metadata CAS
  ├─ JobStageEventsRepository
  └─ JobsService.findOne       ← read enriched job for return paths

JobSummaryService              ← summary workflow
  └─ JobsRepository            ← CRUD + summary metadata CAS

JobsResolver
  ├─ fillJobAutomatically → JobAutomaticFillService
  └─ requestJobSummary    → JobSummaryService
```

## Alternatives Considered

### Alternative 1: `JobFillPersistenceService` + `JobProcessingStateService`

- **Description**: Rename misnamed classes; keep `JobsService.processFillJob()` as fill orchestrator.
- **Pros**: Smaller rename surface.
- **Cons**: Still splits fill across three concepts; CAS service is not a repository but also not domain orchestration.
- **Why rejected**: User chose dedicated feature orchestrators without extra generic status services.

### Alternative 2: Merge CAS into `JobsRepository` only (no separate status service)

- **Description**: Move conditional JSONB SQL onto `JobsRepository`; no `JobProcessingStateService`.
- **Pros**: One write path for job rows; no misnamed repository class.
- **Cons**: Repository grows with optimistic-lock helpers.
- **Why rejected**: Acceptable — helpers stay in `async-metadata.helper.ts`; repository methods remain thin wrappers.

### Alternative 3: Collapse fill TX into `JobsService`

- **Description**: Inline transactional finalize in lifecycle service.
- **Pros**: Fewer injectables.
- **Cons**: `JobsService` already large; mixes lifecycle with async AI workflow.
- **Why rejected**: Fill belongs in `JobAutomaticFillService`.

## Consequences

### Positive

- Clear ownership: lifecycle vs fill vs summary.
- No generic `JobProcessingStateService` or `JobBackgroundTaskStatusService`.
- Resolver and listeners delegate to the right orchestrator.
- Auto-fill gate on create can delegate to `JobAutomaticFillService.fillJobAutomatically()` (ADR-001).

### Negative

- Circular dependency: `JobAutomaticFillService` injects `JobsService` for enriched reads; create gate requires `forwardRef` when `JobsService` injects fill service.
- Mechanical file moves touched many imports and tests.

### Risks

- Transaction regression — mitigated by `jobs-fill.integration.ts` and `job-automatic-fill.service.spec.ts`.

## Implementation Notes

- Files: `job-automatic-fill.service.ts`, `summary/job-summary.service.ts`; deleted `job-fill.persistence.ts`, `job-async-metadata.repository.ts`.
- `jobs.module.ts` registers `JobAutomaticFillService`, `JobSummaryService`; no fill persistence or async-metadata repository providers.
- ADR-001 auto-fill wiring depends on this refactor (now complete).
