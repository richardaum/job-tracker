# ADR-001: Backend Hybrid Auto-Fill Trigger

## Status

Accepted

## Date

2026-05-24

## Context

User settings include `autoFillEnabled`, persisted via `UserSetting` and exposed on the Profile Settings tab. The auto-fill pipeline (`JobAutomaticFillService.fillJobAutomatically` → `FillJobRequested` → `processFillJob`) already exists, but automatic fill is triggered client-side via the `?autoConvert=true` query parameter and `useJobAutoFillFromQuery`. That bypasses the user setting, duplicates logic across web and extension clients, and is inconsistent with auto-summary (which gates on `autoSummaryEnabled` in `SummaryEventListener`).

The PRD requires auto-fill to respect the user toggle while still allowing per-import intent (paste dialog checkbox).

## Decision

Add an optional `autoFill: Boolean` field to `CreateJobInput`. When `JobsService.create()` handles a draft capture (`createAsDraftCapture: true`), after persisting the draft it reads `SettingsService.getSettings(userId)` and calls `fillJobAutomatically(userId, jobId)` **only when** `dto.autoFill === true && settings.autoFillEnabled === true`.

Clients express per-action intent via `autoFill`; the backend enforces the global preference. Explicit manual fill via the `fillJobAutomatically` mutation remains ungated.

## Alternatives Considered

### Alternative 1: Frontend gate only (`?autoConvert=true`)

- **Description**: Keep query-param trigger; `useJobAutoFillFromQuery` reads settings before calling the mutation.
- **Pros**: Minimal API change; fast to ship.
- **Cons**: Setting not enforced server-side; extension can bypass; logic duplicated per client.
- **Why rejected**: Does not meet multi-client enforcement or architectural alignment with auto-summary.

### Alternative 2: Backend-only (no per-action flag)

- **Description**: Auto-fill on every draft create when `autoFillEnabled` is true.
- **Pros**: Simplest server rule.
- **Cons**: Removes per-import override on paste; user cannot save-as-draft without fill when setting is on.
- **Why rejected**: Paste UX requires per-import checkbox independent of global default.

### Alternative 3: Event listener on draft created

- **Description**: New domain event + listener (mirror `SummaryEventListener`).
- **Pros**: Decouples create from fill side-effect.
- **Cons**: Extra event type and listener for a single call site; YAGNI given create already branches on `createAsDraftCapture`.
- **Why rejected**: Over-engineered for one trigger point.

## Consequences

### Positive

- Single enforcement point for `autoFillEnabled` across web, extension, and future clients.
- Per-import intent preserved via `autoFill` input.
- Aligns with documented auto-summary pattern (settings gate on automatic path).

### Negative

- Fill may start before the job detail page opens (SSE must convey status — already implemented).
- Requires coordinated client updates (web paste, extension import, GraphQL codegen).

### Risks

- Double-fill if legacy `?autoConvert=true` path remains — mitigated by ADR-002 hard removal.
- `fillJobAutomatically` throws if fill already in progress — create path must not call when fill metadata is already PROCESSING.

## Implementation Notes

- Gate lives in `JobsService.create()` draft-capture branch only; non-draft creates are unaffected.
- `fillJobAutomatically` already validates PROCESSING state and emits `FillJobRequested`.
- Extension passes `autoFill: true` on import; backend skips when setting is off.
