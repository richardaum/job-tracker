# ADR-003: Shared Settings Automation Pattern

## Status

Accepted

## Date

2026-05-24

## Context

Two user settings control automatic AI workflows: `autoFillEnabled` (draft conversion) and `autoSummaryEnabled` (summary regeneration on job changes). Both toggles exist in Profile Settings; duplicate window wiring already reads settings in `JobsService.create()`. Auto-summary was wired in `SummaryEventListener.handleJobUpdated()`; auto-fill wiring is defined in ADR-001.

Without a documented shared contract, future automation features may diverge (frontend gates, ungated automatic paths, manual actions blocked incorrectly).

## Decision

Adopt a single **Settings Automation Pattern** for all automatic AI side-effects:

| Path type                                     | Setting check                                                               | Example                                              |
| --------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------- |
| **Automatic** (system-triggered)              | Must read `SettingsService.getSettings(userId)` and respect `*Enabled` flag | `JobUpdated` → summary; draft create → fill          |
| **Explicit** (user-initiated mutation/button) | Must **not** check `*Enabled`                                               | `requestJobSummary`, `fillJobAutomatically` mutation |

Automatic paths may additionally require a per-request intent flag (`autoFill` on create) where the UX distinguishes global preference from single-action choice.

This TechSpec implements auto-fill per ADR-001 and documents auto-summary as the existing reference implementation — no functional changes to summary unless tests need alignment.

## Alternatives Considered

### Alternative 1: Document only auto-fill

- **Description**: TechSpec scoped strictly to fill wiring.
- **Pros**: Smaller artifact.
- **Cons**: Pattern remains implicit; next feature repeats discovery.
- **Why rejected**: User chose scope B — fill plus documented alignment.

### Alternative 2: Central `SettingsAutomationService`

- **Description**: New service with `shouldAutoFill(userId, intent)` helpers.
- **Pros**: DRY for multiple flags.
- **Cons**: YAGNI for two call sites; adds abstraction layer.
- **Why rejected**: Inline checks in existing services/listeners suffice.

## Consequences

### Positive

- Predictable behavior for users: toggles affect automatic behavior only.
- Clear onboarding for contributors adding future `*Enabled` settings.

### Negative

- Pattern is convention, not enforced by types — relies on code review and tests.

### Risks

- New `JobUpdated` listeners might forget the setting check — mitigate with listener unit tests mirroring `summary-event.listener.spec.ts`.

## Implementation Notes

- Auto-summary reference: `SummaryEventListener.handleJobUpdated()` — early return when `!settings.autoSummaryEnabled`; delegates to `JobSummaryService.requestSummary`.
- Auto-fill reference: `JobsService.create()` draft branch — when `dto.autoFill && settings.autoFillEnabled`, delegate to `JobAutomaticFillService.fillJobAutomatically`.
- Paste dialog default checkbox: initialize from `settings.autoFillEnabled` (user can override per paste).
