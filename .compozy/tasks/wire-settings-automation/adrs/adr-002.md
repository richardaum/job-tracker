# ADR-002: Hard Cutover — Remove `?autoConvert=true`

## Status

Accepted

## Date

2026-05-24

## Context

Automatic fill was historically triggered when the job detail page loaded with `?autoConvert=true`. With ADR-001, fill starts during `createJob` when `autoFill && autoFillEnabled`. Keeping both paths risks duplicate fill attempts and leaves a URL-based bypass for the user setting.

## Decision

Remove the query-param trigger in the same implementation pass:

- Delete `useJobAutoFillFromQuery.ts` and its usage in `JobDetailsLayout`.
- Stop appending `?autoConvert=true` in `PasteListenerProvider`, extension `ImportJobService`, and e2e tests.
- Update `docs/FEATURE_MAP.md` to describe server-side auto-fill on create.

No transitional fallback reads `?autoConvert` on the frontend.

## Alternatives Considered

### Alternative 1: Transitional dual path

- **Description**: Keep `useJobAutoFillFromQuery` as fallback for one release; log deprecation.
- **Pros**: Safer for stale extension builds and bookmarked URLs.
- **Cons**: Double-fill risk; prolonged dual maintenance; setting bypass window remains.
- **Why rejected**: User chose immediate removal; codebase is monorepo — web and extension ship together.

### Alternative 2: Keep both paths indefinitely

- **Description**: Backend fill on create plus frontend hook.
- **Pros**: Maximum backward compatibility.
- **Cons**: Redundant; race on concurrent triggers.
- **Why rejected**: Unacceptable complexity and correctness risk.

## Consequences

### Positive

- One automatic fill code path; no URL bypass.
- Simpler job detail page (no query-param effect hook).

### Negative

- Old deep links with `?autoConvert=true` become inert (harmless no-op).
- Requires extension update in same release to pass `autoFill: true` on create.

### Risks

- Stale extension build without `autoFill` input — user must update extension; document in release notes.

## Implementation Notes

- Navigation after paste/import becomes `/jobs/{id}` only.
- E2E `draft-conversion.spec.ts` must assert fill via API response (`fillMetadata.status`) or SSE, not query param.
