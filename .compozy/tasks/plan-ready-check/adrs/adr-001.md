# ADR-001: readyCheck — Generic Pre-Collection Stabilization for Plan Steps

## Status

Accepted

## Date

2026-05-31

## Context

The extension's `jobs-list.service.ts` has a hardcoded `waitForTelegramUpdateOrDelay` method that checks for "Updating..." text in `.input-search-placeholder` before collecting jobs. This is Telegram-specific and prevents the extension from working generically across platforms.

The stabilization pattern is: before starting the collection loop, wait for the page to finish any in-progress loading/updating operation. Different platforms signal readiness differently (text change, spinner removal, attribute mutation).

## Decision

Add an optional `readyCheck` configuration block to the `collect.jobs` step input in the plan schema. The config uses an extensible `mode` union (starting with `"text"`) to support different readiness detection strategies.

The content script's `waitForTelegramUpdateOrDelay` is replaced by `waitForReadyCheck(config?)` that only runs once before the collection loop (not after each scroll).

## Alternatives Considered

### Alternative 1: Separate `wait` step kind

- **Description**: A new `PlanStepAction` kind (`wait`) that can be inserted before `collect.jobs`
- **Pros**: Decoupled, reusable across step types
- **Cons**: Increases plan complexity, the wait is inherently tied to the collect step (platform-specific), more boilerplate in plan creation
- **Why rejected**: Stabilization is a property of the collect step, not a standalone operation. Every `collect.jobs` may need it; forcing a separate step adds cognitive overhead.

### Alternative 2: `triggerText`-only config

- **Description**: Schema with `selector` + `triggerText` only, no mode enum
- **Pros**: Simple, covers Telegram case
- **Cons**: Hard to extend for other patterns (spinner removal, attribute change) without breaking change
- **Why rejected**: The mode enum allows adding `"removed"`, `"attribute"`, etc. later without schema migration.

### Alternative 3: Keep hardcoded, parameterize via env/flags

- **Description**: Pass selector/text via runtime config instead of plan schema
- **Pros**: No schema change
- **Cons**: Defeats plan portability, couples platform logic to extension code
- **Why rejected**: The plan is the right abstraction for platform-specific behavior.

## Consequences

### Positive

- New platforms only need a plan change, not extension code changes
- Backward compatible: `readyCheck` is optional, existing plans unchanged
- Mode union allows future detection strategies without breaking changes

### Negative

- Slight increase in plan schema complexity
- Plan authors need to understand when readyCheck is needed

### Risks

- If the selector doesn't exist or timeout expires, the step silently proceeds (by design — avoids brittle failures on DOM variations)
- Low risk: behavior is identical to current hardcoded version for Telegram

## Implementation Notes

- Timeout fields (`resolveTimeoutMs`, `watchTimeoutMs`, `pollIntervalMs`) have sensible defaults
- `selector` is required when `readyCheck` is enabled
- `mode` is `"text"` for now (union type for future extension)
- `value` defaults to `"updating"` when mode is `"text"`
- Content script: `waitForReadyCheck` runs once before the collection loop (lines 93 in current `execute()`)
- The after-scroll call (line 171) is removed
