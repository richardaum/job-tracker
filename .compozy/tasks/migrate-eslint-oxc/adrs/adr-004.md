# ADR-004: Plugin Mapping Strategy — Map All ESLint Plugins to OXC Equivalents

## Status

Accepted

## Date

2026-05-29

## Context

The current ESLint config uses 12 plugins. OXC has built-in native equivalents for most but not all. The user chose to map 1:1 all existing ESLint plugins. This ADR documents the mapping for every plugin and what to do when a native OXC equivalent does not exist.

## Decision

Map each ESLint plugin to its OXC equivalent:

| #   | ESLint Plugin                         | OXC Native Plugin           | Notes                                                                                        |
| --- | ------------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------- |
| 1   | `@eslint/js` (core)                   | `eslint` (default)          | Native, included by default                                                                  |
| 2   | `typescript-eslint`                   | `typescript` (default)      | Native, includes type-aware with `options.typeAware: true`                                   |
| 3   | `eslint-plugin-react`                 | `react` (opt-in)            | Native, covers JSX rules                                                                     |
| 4   | `eslint-plugin-react-hooks`           | Part of `react` plugin      | Native, included in `react` plugin                                                           |
| 5   | `eslint-plugin-react-compiler`        | Not available natively      | Community JS plugin exists (`@TheAlexLichter/oxlint-react-compiler-rules`); use as JS plugin |
| 6   | `eslint-plugin-react-refresh`         | Part of `react` plugin      | Native, included in `react` plugin                                                           |
| 7   | `eslint-plugin-simple-import-sort`    | `import` plugin (opt-in)    | Native `import/order` rule replaces it; see ADR-003                                          |
| 8   | `eslint-plugin-better-tailwindcss`    | Not available natively      | Use as JS plugin via `jsPlugins` config, or rewrite as Rust plugin                           |
| 9   | `@next/eslint-plugin-next`            | `nextjs` (opt-in)           | Native plugin; configure with `settings.next.rootDir`                                        |
| 10  | `eslint-plugin-testing-library`       | Not available natively      | Use as JS plugin via `jsPlugins` config, or rewrite as Rust plugin                           |
| 11  | `eslint-config-prettier`              | Not needed                  | Remove — OXC does not conflict with Prettier                                                 |
| 12  | `globals`                             | `env` + `globals` in config | Native equivalent in OXC config                                                              |
| 13  | `@job-tracker/eslint-plugin` (custom) | Custom Rust plugin          | See ADR-002                                                                                  |

For plugins without native equivalents (react-compiler, better-tailwindcss, testing-library):

- First attempt: use OXC JS Plugins (alpha) to load the ESLint package directly
- Fallback: rewrite as Rust native plugin if JS plugin compatibility is insufficient

The `@oxlint/migrate` tool handles most of this mapping automatically, including generating `jsPlugins` entries for non-native plugins.

## Alternatives Considered

### Alternative 1: Drop non-native plugins

- **Description**: Only configure plugins with native OXC support; drop react-compiler, better-tailwindcss, and testing-library rules.
- **Pros**: Simpler config; no JS plugin dependency.
- **Cons**: Loses validation coverage; user chose 1:1 mapping.
- **Why rejected**: Does not meet the 1:1 coverage requirement.

### Alternative 2: Rewrite all non-native plugins as Rust

- **Description**: Implement better-tailwindcss, testing-library, and react-compiler rules as OXC Rust plugins.
- **Pros**: Full native performance; no alpha JS Plugin dependency.
- **Cons**: Significant development effort (3+ plugin rule sets); not YAGNI.
- **Why rejected**: Over-engineered; JS Plugins (alpha) cover the gap with existing ESLint packages.

## Consequences

### Positive

- Full lint coverage preserved across all current ESLint plugins
- Most plugins are native (fast, no JS overhead)
- Clear migration path for each non-native plugin

### Negative

- JS Plugins are alpha — may break on OXC upgrades; must pin OXC version
- `@oxlint/migrate` output needs manual review and refinement
- `eslint-config-prettier` removal is safe but requires verification

### Risks

- React Compiler rules (`eslint-plugin-react-compiler`) may not work as JS Plugin — community solution exists but is unverified with this codebase
- `eslint-plugin-better-tailwindcss` compatibility with OXC JS Plugins is unknown
