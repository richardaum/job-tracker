# ADR-002: Rewrite Custom ESLint Plugin Rules as OXC Rust Plugins

## Status

Accepted

## Date

2026-05-29

## Context

The project has a custom ESLint plugin at `packages/eslint-plugin/` with two rules:

- `prefer-try-run-over-try-catch` — warns when bare `try/catch` is used without `finally`, preferring `tryRun()` from `@job-tracker/try-run`
- `no-as-unknown-as` — errors on `as unknown as X` double type assertions

OXC does not support running JavaScript-based ESLint plugins natively (JS Plugins are alpha and not suitable for production). The user chose to rewrite both rules as OXC Rust plugins.

## Decision

Rewrite both custom rules as OXC Rust native plugins:

- Create `packages/oxlint-plugin/` (Rust crate) with both rules implemented against the OXC plugin API
- Remove `packages/eslint-plugin/` after the rewrite is complete
- Register the plugin in `.oxlintrc.json` via the `plugins` field
- Rules must match the exact behavior and severity of the current ESLint implementations

## Alternatives Considered

### Alternative 1: Keep ESLint only for custom plugin

- **Description**: Run ESLint with a minimal config just for the 2 custom rules; OXC for everything else.
- **Pros**: Zero rewrite effort; rules continue working as-is.
- **Cons**: Two linters in CI; ESLint startup overhead defeats partial speed gain.
- **Why rejected**: User chose full OXC replacement; no hybrid setup.

### Alternative 2: Use OXC JS Plugins (alpha)

- **Description**: Keep the custom plugin as JS and load it via OXC's `jsPlugins` config.
- **Pros**: No rewrite; OXC JS Plugins use ESLint-compatible API.
- **Cons**: JS Plugins are alpha (no semver); may break on OXC upgrades; slower than native Rust plugin.
- **Why rejected**: User chose Rust rewrite path explicitly.

### Alternative 3: Drop both rules

- **Description**: Remove the custom plugin entirely; accept the patterns as allowed.
- **Pros**: No maintenance; fastest migration.
- **Cons**: Loses enforcement of project-specific conventions (`tryRun` preference, double cast prevention).
- **Why rejected**: Both rules enforce meaningful project conventions.

## Consequences

### Positive

- Native Rust execution — no overhead from JS runtime for plugin rules
- Full control over rule semantics
- No dependency on alpha JS Plugins API

### Negative

- Requires Rust development skills and OXC plugin SDK knowledge
- Review and testing needed to match existing ESLint rule behavior exactly
- New build step for the Rust crate

### Risks

- OXC plugin API may not support all AST patterns used by the current rules — must verify during implementation
- CI must compile the Rust plugin before linting can run
