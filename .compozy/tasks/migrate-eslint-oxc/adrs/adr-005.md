# ADR-005: Progressive Migration by App

## Status

Accepted

## Date

2026-05-29

## Context

The monorepo has 4 apps/packages with lint scripts: `apps/api`, `apps/web`, `apps/extension`, and `packages/ui`. Each runs `eslint` independently via turbo. A big-bang migration of all apps simultaneously carries higher risk of undetected regressions in lint coverage.

The user chose to migrate app by app, validating each before moving to the next.

## Decision

Migrate apps in order: `apps/api` → `apps/web` → `packages/ui` → `apps/extension`.

Each step:

1. Configure the OXC config with appropriate plugins for that app's file types and patterns
2. Run OXC lint on the app, fix all violations or adjust config
3. Update the app's `package.json` lint script from `eslint ...` to `oxlint ...`
4. Run `pnpm typecheck` + `pnpm test` for that app to confirm no breakage
5. Remove ESLint config entries specific to that app's overrides
6. Commit the app's migration before starting the next

The last app to migrate removes the remaining ESLint dependencies and `eslint.config.ts`.

## Alternatives Considered

### Alternative 1: Big-bang migration (all apps at once)

- **Description**: Migrate all apps in a single pass; replace `eslint.config.ts` with `.oxlintrc.json` and update all scripts at once.
- **Pros**: One-shot change; fewer total commits.
- **Cons**: If a plugin is misconfigured for one app, it blocks all apps; harder to isolate per-app regressions.
- **Why rejected**: Higher risk; harder to debug per-app issues.

### Alternative 2: Reverse order (extension first)

- **Description**: Start with the smallest/simplest codebase first.
- **Pros**: Faster validation cycle for early learning.
- **Cons**: Extension uses Tailwind and Testing Library — two plugins lacking native OXC support (see ADR-004); starting with the hardest app first is counterproductive.
- **Why rejected**: API has the simplest plugin requirements (no React, no Tailwind, no Testing Library) — best first candidate.

## Consequences

### Positive

- Each app validated independently — issues isolated to one scope at a time
- Early apps (api → web) build confidence for more complex apps (extension)
- Each step is a self-contained, reviewable commit

### Negative

- More migration steps (4 commits instead of 1)
- ESLint dependencies remain until the last app is migrated

### Risks

- If `packages/eslint-plugin` (custom plugin) is removed mid-migration (step 2/3), ESLint will fail for remaining apps — must keep the plugin until the last app migrates, or remove it after all apps are on OXC
