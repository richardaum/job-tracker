# ADR-002: Record Job Tracker token usage at the AI boundary

## Status

Accepted

## Date

2026-08-20

## Context

The application has many OpenAI callers, including both Chat Completions and Responses APIs. A Profile usage view needs exact aggregate totals for successful Job Tracker calls, split by personal-key and trial access. OpenAI response usage is available at the point each request completes; it cannot be reconstructed reliably afterward.

## Decision

Persist one usage record for every successful OpenAI request at the shared AI boundary. Each record contains the authenticated user, access source (`PersonalKey` or `Trial`), input tokens, output tokens, total tokens, and completion timestamp. Extend the AI chat paths, which bypass the common non-streaming helper, to record the same data. Aggregate records over the prior 30 days through an authenticated GraphQL query.

## Alternatives Considered

### Alternative 1: Add counters to user settings

- **Description**: Maintain mutable totals directly on `user_settings`.
- **Pros**: Simple reads.
- **Cons**: Cannot filter by period or retain personal-key and trial history correctly after a key changes.
- **Why rejected**: The requested rolling 30-day view requires timestamped, source-specific data.

### Alternative 2: Count only in the frontend

- **Description**: Accumulate requests in browser state.
- **Pros**: No database change.
- **Cons**: Misses background work, is not durable, and cannot access provider response usage securely.
- **Why rejected**: Server-side AI calls are authoritative.

## Consequences

### Positive

- Every successful AI feature shares one accounting model.
- Aggregates are exact for measured Job Tracker calls and remain private to the authenticated user.

### Negative

- Historical requests before deployment are unavailable.
- The streaming chat integration needs explicit usage capture.

### Risks

- A malformed provider response could omit usage. Do not create a misleading partial record; log a safe diagnostic and return the original feature response.

## Implementation Notes

Use a TypeORM migration and a dedicated `AiUsageModule`. The resolver only delegates; aggregation and recording stay in the service/repository layers. No raw API key, prompts, completions, or OpenAI response payloads are stored in usage records.
