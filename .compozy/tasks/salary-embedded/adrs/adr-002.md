# ADR-002: API Surface Changes for Salary Embedded

**Status:** Accepted
**Date:** 2026-05-22

## Context

The `SalaryEmbedded` refactor (ADR-001) introduces a nested TypeORM embedded on `JobEntity`. This requires decisions on how the embedded surface is exposed through GraphQL inputs, field resolvers, and repo DTOs.

Previously:

- GraphQL inputs (`CreateJobInput`, `UpdateJobInput`) had 4 flat salary fields
- A dedicated `SalaryResolver` with `@ResolveField` mapped flat entity fields to the nested `JobSalary!` GraphQL output type
- Repo DTOs used `Pick<NewJob, "salaryMinCents" | ...>` to define salary columns
- `SalaryColumns` type derived from entity flat fields

With the embedded, these patterns must change.

## Decision

**1. GraphQL inputs become nested.** `CreateJobInput` and `UpdateJobInput` replace 4 flat salary fields with:

```ts
@Field(() => JobSalaryInput, { nullable: true })
salary?: JobSalaryInput;
```

A new `@InputType() JobSalaryInput` mirrors `JobSalaryType` shape (minCents, maxCents, currency, period). The flat fields are removed from inputs.

**2. Remove `SalaryResolver`.** The `@ResolveField` resolver at `salary/salary.resolver.ts` is deleted. Instead, `JobEntity.salary` is decorated with `@Field(() => JobSalaryType, { nullable: true })`, exposing the embedded directly through TypeGraphQL. This eliminates the flat→nested mapping layer.

**3. GraphQL salary becomes nullable.** The output field changes from `salary: JobSalary!` to `salary: JobSalary`. When `salary` is `null` on the entity, GraphQL returns `null` (instead of an object with all-null fields). Consumer code uses optional chaining (`job.salary?.minCents`).

**4. `SalaryEmbedded` replaces `SalaryColumns` in repo DTOs.** `CreateJobRepoDto` and `UpdateJobRepoDto` drop the 4 flat salary keys from `Pick<>` and instead include `salary?: SalaryEmbedded`. `SalaryColumns` type is removed. `SalaryService` returns `SalaryEmbedded` instances instead of flat objects.

**5. `CreateDto`/`UpdateDto` in `JobsService` become flat passthroughs.** The service-level DTOs keep flat salary fields (matching GraphQL input shape) but delegate conversion to `SalaryService` which now returns `SalaryEmbedded`. The `...salaryColumns` spread in `create()` becomes `salary: salaryEmbedded`.

## Alternatives Considered

### A — Keep flat GraphQL inputs, map internally

Keep inputs flat, convert to embedded inside `SalaryService`. Rejected because it keeps 4-field duplication in inputs and contradicts the "single source of truth" goal. The 4-field shape would still be defined in input types.

### B — Keep SalaryResolver as pass-through

Keep resolver but make it return `app.salary ?? null`. Rejected because it adds an unnecessary indirection layer when TypeGraphQL can expose the embedded directly. A resolver that just returns a property is dead weight.

### C — Keep JobSalary! non-null with default empty embedded

Make `salary` non-optional on entity, always initialized with `new SalaryEmbedded()`. Rejected because it introduces a sentinel object (all-null embedded) that requires `isEmpty()` checks throughout consumer code. Null is a clearer signal.

## Consequences

### Positive

- GraphQL inputs and outputs share the same nested shape (`JobSalaryInput` / `JobSalaryType`), reducing cognitive mismatch
- One less resolver file to maintain
- No `SalaryColumns` flat type to keep in sync
- Repo DTOs directly accept `SalaryEmbedded`, TypeORM handles persistence naturally

### Negative

- GraphQL schema change (inputs + output contract) requires codegen regeneration and frontend adjustment
- `salary: JobSalary!` → `salary: JobSalary` is a breaking contract change (service-layer codegen types change)
- `CreateJobInput`/`UpdateJobInput` lose 4 `@Field` decorators — codegen output in `apps/web/src/gql/` changes

### Risks

- Frontend code may have assumptions about `JobSalary!` being non-null; optional chaining needed
- Migration must coordinate codegen + frontend changes
