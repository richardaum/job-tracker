# ADR-003: Match Analysis Unification — Single Mutation, Single FK

## Status

Accepted

## Date

2026-05-22

## Context

The current architecture has separate match analysis paths for Job and DraftJob:

- `generateJobMatch(jobId, resumeId)` uses `job.description` as text source
- `generateDraftJobMatch(draftJobId, resumeId)` uses `htmlToPlainText(draft.htmlContent)` as text source
- `match_analysis` table has dual nullable FK: `jobId` and `draftJobId`
- Separate resolvers: `JobMatchResolver` (`@ResolveField match` on `JobType`) and `DraftJobMatchResolver` (`@ResolveField match` on `DraftJobType`)
- During draft→job conversion, match analysis is transferred via `UPDATE match_analysis SET job_id = $newJobId WHERE draft_job_id = $draftId`

After merging Draft into Job, there is no more `draftJobId`. Every match analysis target is a Job. The text source selection (description vs htmlContent) becomes an internal implementation detail, not an API distinction.

## Decision

**Unify into a single `generateJobMatch(jobId, resumeId)` mutation with internal source selection.**

- Migration: `UPDATE match_analysis SET job_id = ... WHERE draft_job_id IS NOT NULL`, then `ALTER TABLE match_analysis DROP COLUMN draft_job_id`
- Remove `generateDraftJobMatch` mutation and `DraftJobMatchResolver`
- Remove `draftJob` ManyToOne relation from `MatchAnalysisEntity`
- Internal source selection in `processMatchAnalysis`:
  - If `job.htmlContent` is non-null → use `htmlToPlainText(job.htmlContent)` as text source
  - Else → use `job.description` as text source
- The `@ResolveField match` on `JobType` (via `JobMatchResolver`) remains — it already works with `jobId`

## Alternatives Considered

### Alternative 1: Keep dual FK, add alias path

- **Description**: Keep `draftJobId` column but add a resolver that maps it to `jobId` internally. The column becomes a write-only compatibility shim.
- **Pros**: Zero migration risk for match_analysis data. No data movement.
- **Cons**: Dead column adds confusion. Query complexity (OR conditions on jobId/draftJobId). Violates the "single entity" principle of the merge.
- **Why rejected**: The migration is straightforward (one UPDATE + one DROP). Keeping dead columns undermines the purpose of the merge.

### Alternative 2: Two mutations targeting the same entity

- **Description**: Keep `generateJobMatch` for parsed jobs and `generateDraftJobMatch` for DRAFT-stage jobs, both operating on Job IDs.
- **Pros**: No service logic change during migration phase.
- **Cons**: API surface duplication. Users must know whether their job is DRAFT or parsed to pick the right mutation. Confusing UX.
- **Why rejected**: Having two mutations for the same entity type violates API consistency. The PRD explicitly states match analysis should work regardless of stage.

## Consequences

### Positive

- Single mutation reduces API surface and frontend complexity
- Internal source selection is transparent to callers
- Removes `DraftJobEntity` dependency from match-analysis module
- Simplifies match_analysis entity: single FK, single relation

### Negative

- Migration moves data (`UPDATE` on potentially large table)
- `htmlToPlainText` must handle null safety (htmlContent may be absent for manually created jobs)

### Risks

- **Data migration correctness**: The UPDATE must correctly resolve draft_job_id → job_id. Mitigated by running the migration within the same transaction as the draft→job row migration, ensuring referential integrity.
- **Text source ambiguity**: A job with both `htmlContent` and `description` populated — the fill process populates `description` but keeps `htmlContent`. The selection logic (`htmlContent` preferred) is intentional: after fill, the description is AI-extracted and may differ from the original page content. For match analysis, the original content is the more complete source.
