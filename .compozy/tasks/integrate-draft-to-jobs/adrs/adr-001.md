# ADR-001: Full Merge — Draft as Job Stage

## Status

Accepted

## Date

2026-05-22

## Context

Today Draft (`DraftJobEntity`, table `draft_jobs`) and Job (`JobEntity`, table `jobs`) are separate entities with separate GraphQL types, queries, mutations, frontend routes, and workflows. A "Convert to job" async AI pipeline bridges them: AI extracts structured data from `draft.htmlContent` and creates a new `JobEntity`. This dual-entity model adds complexity across the entire stack — two list pages, two detail pages, separate match analysis mutations, separate SSE streams.

The product goal is to simplify: treat "draft" as a stage in the job lifecycle, not a separate entity. A job starts as DRAFT (raw imported content), can be enriched via "Fill automatically" (AI extraction), and progresses through the normal pipeline (NEW → APPLIED → …).

## Decision

**Full merge: eliminate `DraftJobEntity` and absorb its fields into `JobEntity`.**

- `ApplicationStageEnum` gains `DRAFT`. Draft is a stage, not an entity.
- Draft fields merge into Job: `draft.url` → `Job.urls[]`, `draft.htmlContent` → new `Job.htmlContent` field, `draft.title` → `Job.title` (made nullable).
- `title` becomes nullable to support DRAFT-stage jobs that haven't been parsed yet.
- Route `/draft-jobs` is removed. Drafts appear in `/jobs` filtered by stage=DRAFT via a new "Draft" quick filter.
- Job detail page conditionally shows a "Source content" tab (the former "Captured" tab) when `htmlContent` is present.
- "Fill automatically" replaces "Convert to job". Available on any Job; if stage is DRAFT, it transitions to NEW after successful fill. Otherwise it re-enriches in-place without stage change.
- Match analysis is unified: no separate `generateDraftJobMatch` / `generateJobMatch`. A single `generateJobMatch` works for both DRAFT and parsed jobs (uses `htmlContent` when available, falls back to `description`).
- Existing match data is preserved as-is post-Fill (same behavior as today's conversion transfer).
- Data migration: all `draft_jobs` rows become `jobs` rows with stage=DRAFT. The `draft_jobs` table and `DraftJobEntity` are removed.

## Alternatives Considered

### Alternative 1: Phased Merge

- **Description**: Two-phase transition. Phase 1 adds DRAFT stage and routes new imports to Job, keeping legacy `draft_jobs` read-only. Phase 2 migrates and removes the old table.
- **Pros**: Lower risk per phase, faster time-to-value for Phase 1, easier rollback.
- **Cons**: Dual codebase and dual data model during transition period, higher total effort, temporary complexity in UI (showing both legacy Drafts and DRAFT Jobs).
- **Why rejected**: The user preferred a clean break. The codebase is small enough that a single-phase migration is manageable with proper testing.

## Consequences

### Positive

- Single entity model reduces code surface: one resolver, one service, one repository, one detail page, one list page.
- Match analysis simplifies from two mutations to one.
- No more SSE stream per entity type — Job SSE covers all stages.
- Consistent UX: users interact with Jobs regardless of stage.

### Negative

- Data migration must handle all existing `draft_jobs` rows, linked jobs, and match analysis records referencing `draftJobId`.
- `title` becoming nullable may require null-guard updates across frontend and backend code.
- Browser extension must change from `createDraftJob` to `createJob`.

### Risks

- **Data migration failure**: Mitigated by running migration in a transaction with a rollback plan. Dry-run on a copy of production data first.
- **Frontend regressions**: Many components assume `title` is non-null. Mitigated by systematic grep + typecheck before merge.
- **Extension compatibility**: Old extension versions calling removed mutations will break. Mitigated by coordinating extension release with API deploy.
