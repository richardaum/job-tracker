# ADR-004: Async Fill Tracking — Reuse AsyncMetadataEmbedded

## Status

Accepted

## Date

2026-05-22

## Context

The draft→job conversion pipeline uses `ConversionMetadataEmbedded` (status IDLE/PROCESSING/SUCCEEDED/FAILED, error, timestamp) to track async AI extraction progress. SSE events notify the frontend of status changes.

After merging Draft into Job, the "Fill automatically" action needs the same async tracking: the mutation returns immediately with PROCESSING status while a background worker runs AI extraction. The existing `AsyncMetadataEmbedded` (used by `summaryMetadata`) has the same shape: `{ status, error, generatedAt }`.

## Decision

**Add a `fillMetadata` column to `JobEntity` using the existing `AsyncMetadataEmbedded`.**

- Column: `@Column(() => AsyncMetadataEmbedded, { prefix: "fill" })` → `fill_status`, `fill_error`, `fill_generated_at`
- Reuse the existing `AsyncTaskStatusEnum` (PENDING, PROCESSING, COMPLETED, FAILED)
- Remove `ConversionMetadataEmbedded` and `DraftJobConversionStatusEnum` — they become obsolete
- SSE events emitted on the existing Job SSE stream, not a new controller
- The `DraftJobsSseController` is removed; job fill status flows through the job SSE

Service contract:

```typescript
class JobsService {
  fillJobAutomatically(userId: string, jobId: string): Promise<JobType>;
  processFillJob(userId: string, jobId: string): Promise<void>; // background
}
```

Same concurrency pattern as summary: QueryBuilder atomic update with `WHERE fill_status = expectedStatus`, stale recovery on `OnModuleInit`.

## Alternatives Considered

### Alternative 1: New FillMetadataEmbedded class

- **Description**: Create a dedicated embedded with fill-specific fields (source type, extraction model, etc.).
- **Pros**: More semantic clarity. Room for future fill-specific metadata.
- **Cons**: New embedded class for a single use case. The current AsyncMetadataEmbedded already covers all needed fields. YAGNI — no fill-specific metadata is needed now.
- **Why rejected**: The AsyncMetadataEmbedded pattern is proven and sufficient. A new class adds code without value.

### Alternative 2: Synchronous fill (blocking mutation)

- **Description**: `fillJobAutomatically` blocks until AI extraction completes (~5-15s). No metadata tracking needed.
- **Pros**: Simplest possible implementation. No SSE, no metadata, no background worker. Frontend can use simple loading state.
- **Cons**: HTTP timeouts for slow AI calls (some job descriptions are large). Poor UX — user stares at a spinner with no progress feedback. Blocks the GraphQL connection for other operations in the same session.
- **Why rejected**: Async is the established pattern in this codebase (summary, conversion). Synchronous fill would be a regression in UX and a timeout risk.

## Consequences

### Positive

- Reuses proven pattern (`AsyncMetadataEmbedded`) already battle-tested with `summaryMetadata`
- Same optimistic concurrency and stale recovery as summary
- SSE integration fits naturally into the existing Job SSE stream
- `ConversionMetadataEmbedded` and `DraftJobConversionStatusEnum` are removed — net reduction in types

### Negative

- JobEntity gains one more embedded column, adding to table width
- Background worker for fill adds a new async path that must be monitored

### Risks

- **Stale PROCESSING records on restart**: Mitigated by `OnModuleInit` reset (already implemented pattern for drafts, will be adapted for fillMetadata)
- **Concurrent fill requests**: Mitigated by optimistic concurrency check — if `fillMetadata.status` is already PROCESSING, reject with a clear error
