# ADR-003: Normalized Data Model for AI Conversations

## Status

Accepted

## Date

2026-06-01

## Context

The AI Chat feature needs to persist multiple conversations per job, each with a sequence of user and AI messages. Conversations must be queryable by job, and messages within a conversation must be ordered. Two storage strategies were considered.

## Decision

Use two normalized tables: `ai_conversations` (one row per conversation) and `ai_messages` (one row per message). Follow the existing row-per-entity pattern used by notes (`job_notes`), stage events (`job_stage_events`), and other entities.

## Alternatives Considered

### Single table with JSONB array

- **Description**: Store all messages as a JSONB array column on `ai_conversations`
- **Pros**: Single table, simpler schema, fewer joins
- **Cons**: Cannot query individual messages without loading the entire array; concurrent writes to the array are racy; no referential integrity; harder to paginate
- **Why rejected**: JSONB arrays add complexity for updates and concurrency; the existing codebase consistently uses normalized rows

## Consequences

### Positive

- Each message has a stable, queryable ID
- Concurrent message appends via INSERT, not array mutation
- Consistent with existing entity patterns (notes, events)
- Easy to paginate messages if conversations grow long

### Negative

- Additional table and migration
- Slightly more complex queries (JOIN for conversation + messages)

### Risks

- None significant — pattern is well-established in the codebase

## Implementation Notes

- `ai_conversations`: id (text UUID), job_id (FK to jobs), user_id, title, created_at, updated_at
- `ai_messages`: id (text UUID), conversation_id (FK to conversations), role (enum: user/assistant), content (text), created_at
- Migration: `CREATE TABLE` for both
- Repository: thin CRUD following `notes.repository.ts` pattern
