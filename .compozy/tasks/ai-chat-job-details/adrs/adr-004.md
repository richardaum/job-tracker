# ADR-004: Stream First, Persist AI Message on Completion

## Status

Accepted

## Date

2026-06-01

## Context

When a user submits a question to the AI via the chat panel, the AI response is delivered incrementally via streaming. The system needs to persist the final AI message and deliver tokens to the client in real-time. Two sequencing strategies were considered.

## Decision

Stream the AI response tokens to the client first without creating a DB row. When the stream completes, persist both the user message and the AI message atomically in a single batch insert. The client displays tokens incrementally during streaming and finalizes the message IDs on completion.

Flow:

1. `askAiQuestion` mutation: validates access, starts background AI stream, returns `{ success: true, conversationId }`
2. Client subscribes to `aiMessageStreamed(conversationId)` — receives tokens
3. Tokens arrive via EventBus → Subscription, client appends them incrementally
4. On stream complete, server inserts user message + AI message rows atomically
5. Server emits `AiMessageCompleted` event with both message IDs
6. Client finalizes the message UI with the stable IDs

## Alternatives Considered

### Create message before streaming

- **Description**: Insert AI message row (empty content, status=streaming) before streaming begins, update on completion
- **Pros**: Message ID known from the start; partial messages survive page reload
- **Cons**: Two DB writes per message; stalled writes create orphaned streaming rows; requires status column with cleanup logic
- **Why rejected**: Extra complexity of status management and orphan cleanup outweighs the benefit of early message ID; client can manage optimistic local state during streaming

## Consequences

### Positive

- Single DB write per pair of messages (user + AI) on completion
- No orphaned "streaming" rows to clean up on server restart
- Simpler entity model — no status field needed on ai_messages
- Messages are never in an inconsistent state in the database

### Negative

- Message IDs are not available until stream completes — client references messages by local key during streaming
- If client disconnects mid-stream, partial response is lost (client must refetch job context and retry)
- Subscription event type needs nullable fields for token vs. completion payload

### Risks

- Client disconnect mid-stream: acceptable — user can re-ask the question; server stops streaming on socket close
- Client must buffer/write tokens optimistically: acceptable — standard chat UI pattern

## Implementation Notes

- `AiMessageStreamEvent`: `{ conversationId, token?: string, completed: boolean, userMessageId?: string, aiMessageId?: string }`
- No `status` column on `ai_messages` — messages only exist when fully formed
- `ChatService.askQuestion()` starts AI stream asynchronously, returns immediately
- `ChatRepository.createMessagesBatch()` inserts user + AI messages atomically on stream completion
- Client uses `useState` or local ref to accumulate tokens during streaming, switches to stable message IDs on completion
