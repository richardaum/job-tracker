# ADR-001: CLI-only bulk export/import

## Status

Accepted

## Date

2026-07-26

## Context

The platform currently runs locally and needs to migrate to a cloud environment (Supabase). The primary use case for export/import is instance migration — dump all data from one PostgreSQL instance and load it into another. This is a low-frequency operation (1-2 times per instance migration), not a daily admin workflow.

A full admin UI with preview, validation, and progress bars was considered but rejected — it adds complexity for an operation that happens rarely and is best served by a direct database-level tool. Even a minimal admin tab with two buttons was deemed unnecessary since the admin would already have shell access to run the scripts.

## Decision

**CLI scripts as the sole mechanism** — no admin UI:

1. **CLI export script** (`apps/api/scripts/export-data.ts`): Reads all tables via TypeORM repositories, writes a single structured JSON file. Accepts `DATABASE_URL` via env to target any PostgreSQL instance.

2. **CLI import script** (`apps/api/scripts/import-data.ts`): Reads the JSON file, upserts all entities in dependency order (users → jobs → notes, etc.). Accepts `DATABASE_URL` via env.

3. **Format**: Structured JSON with top-level keys per entity type (`users`, `jobs`, `companies`, etc.), preserving relationships via foreign key references.

No admin tab, no GraphQL mutations, no browser-based flow. The operator runs the scripts directly from the terminal.

## Alternatives Considered

### Alternative 1: CLI scripts + admin Data tab

- **Description**: CLI scripts as primary mechanism plus a "Data" tab in the admin panel with Export/Import buttons calling GraphQL mutations.
- **Pros**: Convenience for admins who prefer browser over terminal.
- **Cons**: Extra code (GraphQL mutations, admin tab UI) for a feature used 1-2x. Browser file size limits constrain large datasets. Admin would already have shell access to run scripts.
- **Why rejected**: The added convenience does not justify the implementation cost. Shell access is a prerequisite for running the platform anyway.

### Alternative 2: Raw pg_dump / pg_restore

- **Description**: Use PostgreSQL's native `pg_dump` and `pg_restore` for binary or SQL-format dumps.
- **Pros**: Zero code to write. Fastest for large datasets. Handles all PostgreSQL-specific types natively.
- **Cons**: Tightly coupled to PostgreSQL version. No cross-provider compatibility. Requires shell access to both source and target instances.
- **Why rejected**: While feasible for a one-time migration, an application-level export provides a future-proof backup format and diagnostic tool independent of PostgreSQL internals.

## Consequences

### Positive

- Minimal code surface — two CLI scripts, no UI, no GraphQL layer
- Database-agnostic JSON format works across PostgreSQL versions and providers
- No request-size or timeout concerns since CLI runs unbounded
- JSON exports are human-readable for debugging and manual inspection

### Negative

- No browser-based trigger — requires terminal access
- JSON export may be larger than pg_dump binary format for large datasets
- No built-in conflict resolution for import — uses upsert by primary key, which may not handle all edge cases (e.g., migrating into a non-empty database)

### Risks

- Import into non-empty database may cause unexpected results. Mitigation: document that import targets a fresh database; upsert handles idempotent re-imports.
- Schema drift between export and import instances. Mitigation: document that both instances must run the same migration state.

## Implementation Notes

- Use `NestFactory.createApplicationContext` for CLI scripts to bootstrap DI (pattern from existing `apps/api/scripts/` datafix scripts)
- Export excludes system-wide tables without `userId` (`exchange_rate`) — those are seed/env data, not user data
- Export excludes auth-sensitive fields (`tokenVersion`, `refreshJti`) — those are runtime auth state, not portable data
- Import uses `INSERT ... ON CONFLICT (id) DO UPDATE` (upsert) via TypeORM `.save()` or raw query builder
- Import processes entities in topological order to respect foreign key constraints
