# ADR-006: Add REJECTED to ApplicationQuickFilter Enum

## Status

Accepted

## Date

2026-05-29

## Context

The PRD goal #3 states: "Provide a quick filter (REJECTED) so blocked jobs remain inspectable." The PRD also claims "The existing ApplicationQuickFilter enum already has REJECTED." However, the current `ApplicationQuickFilterEnum` only contains: `DRAFT`, `INCOMING`, `ACTIVE`, `APPLIED`, `NEW`, `DUPLICATED`.

Without a REJECTED quick filter, auto-blocked jobs are effectively invisible to the user — there is no easy way to find them in the jobs list. The only workaround would be to remember the job ID and navigate directly, or to change the filter to "All" (which includes REJECTED) and scroll through every job.

## Decision

Add `REJECTED` to `ApplicationQuickFilterEnum` in the API and update the frontend `QuickFilters` UI to include a REJECTED chip. This gives users a dedicated filter to inspect all blocked and manually rejected jobs.

## Alternatives Considered

### Alternative 1: Use "All" filter (status quo)

- **Description**: The existing "All" quick filter already includes REJECTED jobs. Users could select "All" to see everything including rejected jobs.
- **Pros**: Zero implementation work.
- **Cons**: "All" shows every stage — impossible to find rejected jobs among hundreds of active ones. Defeats the PRD goal of providing a dedicated REJECTED filter.

### Alternative 2: Skip REJECTED filter for v1

- **Description**: Users inspect blocked jobs only through the Notes tab on individual job detail pages (if they know the job ID).
- **Pros**: Simplest approach for v1.
- **Cons**: Blocked jobs are effectively invisible — contradicts PRD goal #3 directly. The Notes traceability is only useful if the user can find the blocked job first.

## Consequences

### Positive

- REJECTED jobs become discoverable with one click.
- Follows existing pattern — each quick filter value maps to a stage-based query.
- Consistent with how DUPLICATED already has a quick filter.

### Negative

- The REJECTED filter will show ALL rejected jobs (manual + auto-blocked), not just auto-blocked ones. This is acceptable per PRD UX: "No visual distinction between manually rejected and auto-blocked jobs."
- Slight UI clutter — one more chip in the QuickFilters row.

## Implementation Notes

- API: Add `REJECTED` to `ApplicationQuickFilterEnum` in `apps/api/src/domains/jobs/job-quick-filter.enum.ts`.
- Frontend: The `useQuickFilter` hook and QuickFilters UI will pick up the new value after codegen.
- The `JobsListQuery.findAllByUserId()` needs to handle `REJECTED` in the query builder — currently REJECTED is excluded from `ACTIVE` and `INCOMING`. Add a case for `REJECTED` similar to `DUPLICATED`.
- Run codegen after PM2 restart to regenerate frontend enum.
