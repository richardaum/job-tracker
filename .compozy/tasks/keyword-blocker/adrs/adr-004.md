# ADR-004: Keyword Blocking Runs Before Duplicate Detection

## Status

Accepted

## Date

2026-05-29

## Context

When a job is created, the system currently checks for duplicates by comparing title and company against recent jobs within a configurable window (`duplicateWindowDays`). If a match is found, the job is assigned stage `DUPLICATED` instead of `NEW`. The keyword blocker needs to integrate with this flow — the question is at which point.

The blocker expresses user intent ("I do not want jobs of this type") which should take priority over any other classification. A user who blocked "QA Engineer" in title wants every job with that title rejected, even if the same company posts the same role again.

## Decision

Keyword blocking runs **before** duplicate detection, as the first stage-determination step after data normalization. If a keyword matches, the job is assigned `REJECTED` immediately and duplicate detection is skipped entirely.

Order in `JobsService.create()`:

1. Normalize input data (company, salary, tags, urls, content)
2. **Check keyword blocker** — if match → REJECTED, skip step 3
3. Check duplicates → DUPLICATED or NEW
4. Create stage event
5. Create auto-generated Note (best-effort)
6. Emit `JobCreated`

## Alternatives Considered

### Alternative 1: Block after duplicate, override

- **Description**: Run duplicate detection first, then check blocker. If blocker matches, override DUPLICATED or NEW with REJECTED.
- **Pros**: Duplicate metrics remain accurate (all duplicates counted before blocker).
- **Cons**: Wasteful — runs duplicate query when result will be discarded. Semantically odd: duplicate check might match on "same company same title" even though the user explicitly blocked that title.

### Alternative 2: Block after duplicate, non-duplicates only

- **Description**: Run duplicate detection first. Only check blocker on non-duplicate jobs (stage = NEW).
- **Pros**: Fewer blocker checks.
- **Cons**: Contradicts user intent — a user who blocked "QA Engineer" in title still sees duplicates of QA Engineer jobs in their list.

## Consequences

### Positive

- User blocking intent takes priority over all other stage logic.
- Avoids unnecessary duplicate queries when blocker matches.
- Simple to implement — single early-exit in the creation flow.

### Negative

- Duplicate detection never runs on blocked jobs, so duplicate metrics may undercount for those jobs.

### Risks

- If blocker is slow (large keyword list), it could impact creation latency for all jobs. Mitigation: blocker runs after normalization (minimal work before it), and keyword list is bounded by user setting JSONB size.

## Implementation Notes

- Place the blocker check between `resolveCompanyId()` / normalization and `resolveInitialStageOnCreate()`.
- If blocker triggers, skip `setPersistedStage()` call from duplicate service — call it directly with `REJECTED`.
- The `stageEvent` creation should use source `SYSTEM` for the REJECTED event.
