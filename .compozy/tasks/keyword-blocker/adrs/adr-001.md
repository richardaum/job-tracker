# ADR-001: Structured Keyword Blocking with Per-Keyword Scope

**Status:** Accepted  
**Date:** 2026-05-27  
**Context:** Implement keyword blocking for jobs based on legacy SQLite forbidden_keywords data and user requirements.

## Decision

Adopt a structured keyword model where each blocking entry has an explicit `scope` (`TITLE`, `DESCRIPTION`, `COMPANY`) and `matchMode` (`PARTIAL`, `EXACT`), stored as a JSONB array in user settings alongside a separate `blockedCompanies` list. This preserves the granularity of the legacy SQLite schema and allows the user to decide which field each keyword targets.

## Alternatives Considered

### A) Simple blocking list

A flat `blockedKeywords: [String!]` field in user settings, checked against title and description globally.  
_Pro:_ Simplest MVP.  
_Con:_ Cannot differentiate "block in title only" vs "block in description only" — losing the `type` column granularity from the existing SQLite data.

### C) Blocking with auto-learning

Same as A, but with an allowlist override mechanism and automatic suggestion when user manually rejects a job.  
_Pro:_ Learns from user behavior.  
_Con:_ Unnecessary complexity for v1; risks over-blocking jobs the user wants to see.

## Consequences

- Keyword blocking data requires a JSONB column on `user_settings` or a new entity (prefer JSONB for v1 simplicity).
- Datafix script to upsert legacy keywords must map `title` → `TITLE`, `partial` → `DESCRIPTION`, `company` → `COMPANY` scopes.
- UI in Settings needs structured fields (scope selector per keyword) — slightly more complex than a flat list.
- Future migration from JSONB to a separate entity is straightforward if needed.
