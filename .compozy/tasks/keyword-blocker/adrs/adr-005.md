# ADR-005: Auto-Note Creation via NotesModule Import and Plain-Text Method

## Status

Accepted

## Date

2026-05-29

## Context

When a job is auto-rejected, an auto-generated Note is created documenting the matched keyword and scope. The `JobsModule` does not currently import `NotesModule` — the note service is not available in the job creation flow. Three approaches exist:

1. Import `NotesModule` into `JobsModule` and use `NoteService` directly.
2. Emit a domain event from the blocker and handle it in a separate listener.
3. Use `NoteRepository` directly bypassing the service layer.

The existing `NoteService.createNote()` validates the content as a TipTap JSON document, but the auto-generated note content is plain text — validation would reject it.

## Decision

Import `NotesModule` into `JobsModule` and add a `createPlainTextNote(jobId, userId, content)` method to `NoteService` that skips TipTap validation. Use `tryRun()` from `@job-tracker/try-run` to wrap the call — note creation is best-effort and must not fail job creation.

## Alternatives Considered

### Alternative 1: Domain event listener

- **Description**: `JobsService` emits a `JobBlocked` event after stage assignment. A separate listener in `NotesModule` subscribes and creates the note.
- **Pros**: No circular dependency risk; loose coupling; note creation logic stays in NotesModule.
- **Cons**: Async — note may be created after the response is sent (in-process event bus). Adds an event class, a listener, and event bus wiring. Overkill for a synchronous side effect.

### Alternative 2: NoteRepository direct

- **Description**: `JobsService` calls `NoteRepository.create()` directly, bypassing `NoteService`.
- **Pros**: Minimal wiring — just inject the repository.
- **Cons**: Violates thin repository pattern (service owns orchestration, repository owns data access). Bypasses NoteService validations and revision tracking.

## Consequences

### Positive

- Simple wiring: one module import, one new method on NoteService.
- Plain-text note creation avoids TipTap validation that would reject the content.
- `tryRun` ensures unavailability of Notes does not block job creation.
- Reuses existing Note entity, repository, and DB table.

### Negative

- `JobsModule` gains a dependency on `NotesModule` (and transitively, its imports).
- `NoteService` gets a second creation path that bypasses TipTap validation — callers must know when to use each path.

### Risks

- Circular dependency if `NotesModule` ever depends on `JobsModule`. Not a risk today. Mitigation: if circular deps arise later, extract the plain-text note creation to a shared service or use the event pattern instead.

## Implementation Notes

- New method on `NoteService`: `async createPlainTextNote(userId, dto)` — no TipTap validation, no revision tracking.
- `JobsService.create()` calls `tryRun(this.noteService.createPlainTextNote(...))` after stage event creation.
- Note content format: `Auto-rejected by keyword blocker: keyword "<term>" matched in <scope>`.
