# ADR-002: Separate GraphQL Query for Filter Counts

## Status

Accepted

## Date

2026-07-25

## Context

The `jobs` query currently returns `[JobType!]!` — a bare array. To expose quick filter counts, the API must include aggregate data. Two approaches: (A) wrap the `jobs` query return type in a payload with both items and counts, or (B) add a new independent query `quickFilterCounts` that returns counts separately.

The user prefers the separate query approach to avoid changing the existing `jobs` query signature and to allow independent caching and refetching.

## Decision

Add a new top-level GraphQL query `quickFilterCounts` that returns filter counts independently:

```graphql
type Query {
  jobs(filter: ApplicationQuickFilter, company: String, runId: ID): [JobType!]!
  quickFilterCounts(company: String, runId: ID): [FilterCount!]!
}
```

The existing `jobs` query stays unchanged. The new query shares the same auth guards (`JwtAuthGuard`, `RolesGuard`, `RoleEnum.User`) as `jobs`.

## Alternatives Considered

### Alternative 1: Wrapper type `JobsPaginated`

- **Description**: Change `jobs` return type to `JobsPaginated { items, filterCounts }`.
- **Pros**: Single round-trip, guaranteed consistency between list and counts.
- **Cons**: Breaks all existing `data.jobs` callers (13+ sites), requires migration of every accessor.
- **Why rejected**: The user prefers zero migration cost. The separate query avoids touching the existing query contract.

## Consequences

### Positive

- Zero migration — existing `jobs` query and all its callers unchanged
- Independent caching — counts can be refetched without refetching the job list
- Simpler front-end integration — only `QuickFilters` needs to use the new query
- New query is optional — if it fails, the list still renders

### Negative

- Two round-trips on page load (list + counts) instead of one
- Counts and list can briefly fall out of sync if mutation refetches one but not the other
- Mutations that affect counts need to explicitly refetch the new query

### Risks

- **Mutual refetch consistency**: After a mutation, both list and counts must be refetched. Mitigation: add `QuickFilterCountsDocument` alongside `JobsDocument` in `refetchQueries` for list-page mutations.
- **Extra network request**: The count query is lightweight (single COUNT aggregate) — negligible overhead.
