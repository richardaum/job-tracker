# ADR-003: Single Aggregate Query for Filter Counts

## Status

Accepted

## Date

2026-07-25

## Context

The backend needs to compute 7 filter counts (All, Draft, Incoming, Active, Applied, New, Duplicated, Rejected) efficiently. Each filter has a different WHERE predicate. Two strategies: (A) one query with CASE + GROUP BY that computes all counts in a single round-trip, or (B) reuse the existing filter logic 7 times with COUNT.

The filter predicates for Incoming and Active are non-trivial — they use subqueries against the latest stage event. A single SQL query can compute all counts in one pass.

## Decision

Implement a single aggregate query in `JobsListQuery` that computes all filter counts in one round-trip. The query uses the same base joins and user/company/runId filters as `findAllByUserId`, but replaces the SELECT with COUNT + CASE expressions:

```sql
SELECT
  COUNT(*) FILTER (WHERE latest_stage IS NULL) AS "all",
  COUNT(*) FILTER (WHERE latest_stage = 'Draft') AS draft,
  COUNT(*) FILTER (WHERE latest_stage NOT IN ('Applied', 'Rejected', 'Duplicated', 'Draft') AND scheduled >= today) AS incoming,
  COUNT(*) FILTER (WHERE latest_stage NOT IN ('New', 'Applied', 'Rejected', 'Duplicated', 'Draft')) AS active,
  COUNT(*) FILTER (WHERE latest_stage = 'Applied') AS applied,
  COUNT(*) FILTER (WHERE latest_stage = 'New') AS new,
  COUNT(*) FILTER (WHERE latest_stage = 'Duplicated') AS duplicated,
  COUNT(*) FILTER (WHERE latest_stage = 'Rejected') AS rejected
FROM (
  SELECT DISTINCT ON (a.id) a.id,
    (SELECT e.to_stage FROM job_stage_events e
     WHERE e.job_id = a.id AND e.user_id = :userId
     ORDER BY COALESCE(e.schedule_at, e.created_at) DESC, e.created_at DESC, e.id DESC
     LIMIT 1) AS latest_stage,
    a.stage,
    a.scheduled_at
  FROM applications a
  WHERE a.user_id = :userId
) sub
```

## Alternatives Considered

### Alternative 1: Seven individual COUNT queries

- **Description**: Call the existing filter logic 7 times with `COUNT(*)` instead of `SELECT *`.
- **Pros**: Reuses tested filter predicates verbatim. No new query logic.
- **Cons**: 7 round-trips to PostgreSQL. Scales linearly with filter count.
- **Why rejected**: The aggregate approach is equally maintainable and significantly more efficient.

## Consequences

### Positive

- Single database round-trip for all 7 counts
- Consistent with the list query — same base data, same user/company/runId filters

### Negative

- New SQL logic that must be tested independently
- The aggregate query duplicates the filter predicate logic (must keep it in sync with `findAllByUserId`)
