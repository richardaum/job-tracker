# ADR-003: Centralized AI Gating in AiBaseService.callAi()

## Status

Accepted

## Date

2026-07-30

## Context

Nine distinct services (`ai-chat-generation.service.ts`, `notes/ai/note-generation.service.ts`, `match-analysis-ai.service.ts`, `jobs/ai/draft-extraction.service.ts`, `jobs/summary/summary-ai.service.ts`, `companies/ai/company-description.service.ts`, `lib/ai/rewrite-text.service.ts`, `lib/ai/restructure-jd.service.ts`, `lib/ai/location-inference.service.ts`) all extend `AiBaseService` and call its single public method, `callAi()`, which resolves the OpenAI client (`OpenAIClient.getClient()`) before making a request. The PRD requires every one of these to consistently enforce: AI toggle on AND (personal key present OR trial quota remaining) before executing. The TechSpec needs to decide where this check lives.

## Decision

Implement the gating check inside `AiBaseService.callAi()`, resolving the user's key (decrypting from `UserSettingEntity` if present, otherwise falling back to the shared system key while consuming trial quota) and enforcing the toggle/quota rule in one place. `CallAiOptions` gains a required `userId` field, threaded in by each of the 9 subclasses from context they already have (the authenticated user is already available to every resolver that triggers these services). A dedicated exception (see TechSpec's API Design) is thrown from this single location when gating fails.

## Alternatives Considered

### Alternative 1: NestJS Guard on each of the 9 resolvers

- **Description**: A new `AiAccessGuard`, following the existing `JwtAuthGuard` pattern (overriding `getRequest` via `GqlExecutionContext`), applied via `@UseGuards(AiAccessGuard)` on each of the 9 resolver mutations/queries that trigger AI.
- **Pros**: Idiomatic NestJS request-pipeline pattern; consistent with how authentication is already enforced.
- **Cons**: Requires modifying 9 separate resolver files instead of 1 service method; a new AI-triggering resolver added later must remember to apply the guard, whereas extending `AiBaseService` automatically inherits gating. Guards also operate before the resolver's business logic, so per-user key resolution (needed for the actual API call, not just gating) would still need to happen separately inside `callAi()` — duplicating the "does this user have a valid key" lookup in two places.
- **Why rejected**: Splits key-resolution and gating-enforcement into two separate locations for no benefit, and creates a maintenance trap where future AI features could ship without the guard attached.

## Consequences

### Positive

- Single, unavoidable enforcement point — every current and future consumer of `AiBaseService.callAi()` is automatically gated with no per-feature opt-in step.
- Key resolution (decrypt stored key vs. fall back to system key) and gating enforcement live together, avoiding duplicated lookups.

### Negative

- `CallAiOptions` signature change (`userId` now required) touches all 9 call sites, even though the gating logic itself lives in one place.

### Risks

- If a future AI feature bypasses `AiBaseService` entirely (calls `OpenAIClient` directly), it would skip gating. Mitigation: `OpenAIClient.getClient()` remains a low-level method; the TechSpec documents that all AI features must go through `AiBaseService`.
