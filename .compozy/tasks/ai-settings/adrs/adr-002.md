# ADR-002: Server-Side Encrypted Storage of Per-User OpenAI Key

## Status

Accepted

## Date

2026-07-30

## Context

The PRD requires each user to supply their own OpenAI API key, persisted through the existing Profile Settings tab so it's available across devices. The key is a secret and must never be stored in plaintext. The codebase has no existing field-level encryption, KMS integration, or secrets-management capability — this is new ground. During TechSpec brainstorming, a client-side alternative (never persisting the key server-side, keeping it only in the browser's localStorage) was raised and evaluated alongside two server-side storage options.

## Decision

Store the key server-side, as a new encrypted column (`openaiApiKeyEncrypted`) on the existing `UserSettingEntity`/`user_settings` table, encrypted at the application layer with AES-256-GCM via a TypeORM column transformer. The transformer encrypts on write and decrypts on read using a single master key held in a new environment variable (e.g., `SETTINGS_ENCRYPTION_KEY`), validated through the existing zod schema in `apps/api/src/env/server.ts` alongside other server config. No new external service or infrastructure dependency is introduced.

## Alternatives Considered

### Alternative 1: Client-side only (localStorage, never persisted server-side)

- **Description**: The key lives only in the browser's localStorage and is attached as an argument to every AI-triggering GraphQL request; the backend never stores it, only a `keyConfigured` boolean for gating purposes.
- **Pros**: Removes the need for any server-side encryption; the operator never holds the raw secret at rest.
- **Cons**: Breaks cross-device sync that the existing Profile Settings model (Identity, Resumes, Work Preferences, Settings tabs) already establishes — a user would need to re-enter the key on every browser/device. Requires threading the key as a parameter through all 9 AI call sites on both frontend and backend, defeating the single-choke-point design in `AiBaseService.callAi()` (ADR-003). The key still transits the network on every AI call instead of once at save time, and remains exposed to the same XSS risk in localStorage as any in-memory value would be.
- **Why rejected**: Contradicts the profile-settings mental model established by the shipped user-profile feature, and increases (not decreases) the surface area touched per the single-choke-point architecture already chosen for gating.

### Alternative 2: Managed KMS service (AWS KMS / Vault)

- **Description**: Encrypt/decrypt the key through a managed key-management service instead of an application-level master key.
- **Pros**: Built-in master-key rotation, audit logging, and separation of the encryption key from application config.
- **Cons**: No managed KMS offers a genuinely free tier at this project's scale (AWS KMS charges ~$1/month per CMK beyond the request free tier; Google Cloud KMS charges per key-version/month); self-hosting Vault trades license cost for operational burden (running, unsealing, backing up a new service) the project does not currently have.
- **Why rejected**: Introduces a new infrastructure dependency and recurring cost/operational overhead not justified at current scale; can be revisited if key rotation or compliance requirements emerge later.

## Consequences

### Positive

- No new infrastructure or paid service required; encryption is self-contained in the API using Node's native `crypto` module.
- Preserves cross-device access to the key via the existing Profile Settings sync model.
- Keeps the key resolution inside the existing single choke point (`AiBaseService.callAi()`), consistent with ADR-003.

### Negative

- The master key is a new secret the operator must manage (store, back up, never rotate without a migration plan for re-encrypting existing rows).
- No built-in key rotation or audit trail — if compromised, the master key must be rotated manually with a re-encryption pass over `user_settings`.

### Risks

- Master key leakage (e.g., committed to version control, exposed in logs) would compromise all stored user keys at once. Mitigation: treat `SETTINGS_ENCRYPTION_KEY` with the same handling as other production secrets (deployment platform's secret store, never in `.env` files committed to the repo).

## Implementation Notes

- New TypeORM migration adds `openai_api_key_encrypted` (text, nullable) to `user_settings`.
- Column transformer implemented once (e.g., `apps/api/src/lib/crypto/encrypted-column.transformer.ts`) and reused for the new column; no per-field custom logic needed.
- Validation call to OpenAI on save uses `GET /v1/models` (no token cost) — see TechSpec for details.
