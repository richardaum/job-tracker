# ADR-002: Non-Active Login Outcomes Communicated via OAuth Callback Redirect

## Status

Accepted

## Date

2026-08-16

## Context

`UserEntity.status` (see [ADR-001](adr-001.md)) can be `pending`, `active`, `rejected`, or `deactivated`. Only `active` accounts should complete authentication. Today, the Google OAuth callback flow authenticates first and only then would discover a blocking status — by the time any check runs, the frontend has no channel to learn _why_ it was blocked beyond a generic HTTP error, since no session or token exists for a non-active account.

The pending-approval and rejected screens (PRD: "Pending approval screen", "Rejected-request re-login handling") require the frontend to distinguish these two outcomes without a valid session.

## Decision

The `/auth/google/callback` handler checks `status` before issuing any session/token. For `pending` and `rejected`, it redirects to the frontend with the outcome encoded as a query parameter (e.g. `/login?status=pending` / `/login?status=rejected`) instead of completing authentication or throwing an unhandled error. The frontend reads this parameter to render the corresponding screen. For `active`, the flow proceeds exactly as today, issuing the normal session.

## Alternatives Considered

**Issue a limited-scope token for non-active accounts, let `me` report status.** Would let the frontend use its existing authenticated-query machinery to fetch status. Rejected because it means tokens now exist for accounts that must not have product access, widening the surface that has to correctly enforce "not active" on every subsequent request — a bigger, riskier change to the auth flow for a gate meant to be temporary.

## Consequences

- The `pending`/`rejected` screens are unauthenticated routes, reachable purely from the redirect — no `me` query involved.
- Any future login-blocking status must extend this same callback branch and pick a query-param value; this is the single place that decides what a blocked login shows.
- No token is ever issued to a non-`active` account, keeping "has a valid session" and "has product access" equivalent, as they are today.
