# ADR-001: Registration Gate Creates a User Row on First Login, Governed by a Unified Status Enum

## Status

Accepted

## Date

2026-08-16

## Context

The product needs a temporary, admin-controlled gate on who can access the job tracker while self-registration is not yet fully open. Access is granted via Google OAuth only — there is no email/password signup form. Today, `UsersService.upsertFromProvider` creates a user record automatically on the very first Google login, with no gating, and `UserEntity.active` (a boolean) is the sole mechanism for excluding a user from the product (used today only for manual deactivation).

Two questions had to be settled together, since they affect the same data model:

1. **When is the user account created?** Immediately on first login attempt (inactive until approved) vs. deferred entirely until an admin approves.
2. **How is account state represented?** Keep `active: boolean` and bolt a separate approval-tracking record onto it, vs. evolve `active` into a single `status` field that expresses every state the account can be in.

## Decision

Create the user account on first login. When gating is active and the email has no prior approval, the account is created with `status = pending` instead of being activated immediately.

Replace `UserEntity.active: boolean` with `UserEntity.status`, an enum with four values: `pending`, `active`, `rejected`, `deactivated`. This single field now drives both the registration gate (`pending`/`rejected`) and the pre-existing manual deactivation mechanism (`deactivated`), which previously used `active = false` for the same purpose. No separate `registration_request` table is introduced — `UserEntity` already carries `email`, `name`, `avatarUrl`, and `createdAt`, which is sufficient for the admin approval screen (request date = `createdAt`).

The Google auth strategy's existing login block (previously `!user.active`) becomes `user.status !== "active"`, so admission control still requires no new authorization code path — only the values `status` can hold, and what creates a `pending` row, change.

## Alternatives Considered

**Defer user creation until approval.** Keeps the `users` table limited to real, approved accounts only — no rejected/pending rows to reason about. Rejected because it requires restructuring the current login flow (which always creates-or-finds the user before any active check) into a new pre-account request path, and duplicates identity data (email, name, avatar) that has to be reconciled with `UserEntity` once approved. Given the temporary nature of this gate, the added structural change was judged not worth it.

**Keep `active: boolean` untouched, add a separate `registration_request` table/status for approval tracking only.** Avoids touching the existing deactivation mechanism at all. Rejected because it would require joining two sources of truth (`users.active` and `registration_request.status`) to know whether someone can log in, and duplicates the same identity fields (email, name, avatar, request date) that already live on `UserEntity`. A single `status` enum is simpler and removes an entire table.

## Consequences

- Rejected or abandoned registration attempts leave `status = rejected` (or `pending`) `UserEntity` rows in the database; these are not deleted.
- Every existing read/write of `UserEntity.active` must be migrated to the new `status` enum (Google strategy login check, admin user tooling, any deactivation code path). This is a broader touch than a purely additive change, but keeps the account-state model as a single source of truth.
- Approval is a one-time, permanent grant (`status` set to `active`); it does not depend on the PostHog flag staying off or on afterward, per product decision.
- The manual deactivation feature (previously "set `active = false`") now sets `status = deactivated`, distinguishing it from a never-approved (`rejected`) account — a minor behavioral improvement, not just a rename.
