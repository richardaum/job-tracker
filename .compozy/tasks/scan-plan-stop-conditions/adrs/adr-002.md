# ADR-002: Extension-driven duplicate check via dedicated GraphQL query

## Status

Accepted

## Date

2026-05-30

## Context

The CatchUp stop condition requires the extension to detect when a collected job already exists in the user's database. The server's `createJob` mutation already runs duplicate detection (`JobDuplicateService`) and sets the job's stage to `DUPLICATED`, but the extension's `CreateJob` GraphQL document does not request `currentStage` in the response, and the extension discards the mutation result anyway.

Two approaches emerged: (a) add `currentStage` to the `CreateJob` response and read it from the mutation result, or (b) add a dedicated read-only `isJobDuplicate` query that checks before creating.

## Decision

Add a dedicated `isJobDuplicate` GraphQL query. The extension calls this query for each collected job before (or alongside) `createJob`. The collector (`CollectJobsService`) receives the duplicate signal and tracks consecutive duplicates. When the threshold is reached, it stops navigating to further pages.

The `onJobCollected` callback returns `{ duplicate: boolean }` so the collector can track the counter.

## Alternatives Considered

### Alternative 1: Read `currentStage` from `createJob` response

- **Description**: Add `currentStage` to the `CreateJob` GraphQL document. After creating each job, read `currentStage` to know if it was `DUPLICATED`.
- **Pros**: No new query, no additional server endpoint. Zero new server code.
- **Cons**: Cannot skip creation of duplicates in the final batch (when threshold is already hit). The mutation created a job that will be a duplicate — wasted DB write.
- **Why rejected**: The dedicated query is cleaner separation of concerns. The read-before-write pattern allows the extension to stop early without persisting unnecessary duplicates from the last page.

## Consequences

### Positive

- Read-before-write pattern: the extension can stop creating jobs from the last page once the threshold is hit
- No side effects from checking duplicate status
- The query is reusable for other features (UI indicators, bulk checks)

### Negative

- Additional GraphQL round-trip per job (the query replaces the need for `currentStage` in the mutation response, but it's a separate call)
- New server-side resolver and GraphQL schema change

### Risks

- Latency: each `collect.jobs` step will make N extra queries (one per job). Mitigation: the query is lightweight (single indexed DB query), and job collection is already I/O-bound.

## Implementation Notes

- New query: `isJobDuplicate(company: String!, title: String!): Boolean!`
- Server resolves company name to company ID, then runs the same logic as `JobDuplicateService.hasRecentDuplicateSameRoleAndCompany`
- Extension calls before `onJobCollected` creation — or inside the callback
- `onJobCollected` changes from `Promise<void>` to `Promise<{ duplicate: boolean } | void>`
- `CollectJobsService` tracks consecutive duplicates per session and stops navigating pages when threshold reached
