# ADR-001: Board type in Plan document JSONB; stop conditions in SourceTemplate

## Status

Accepted (revised)

## Date

2026-05-30

## Context

Scanning behavior depends on two categories of configuration:

1. **Board characteristics** — whether jobs appear in sequential order or not. This is inherent to the job board itself, known by the admin who creates the Plan. It does not vary between users.

2. **User stop preference** — when to stop scanning. This is a user decision: how aggressive to be with CatchUp, how many pages to allow on first runs, or how old a job may be. Different users may want different behavior on the same board.

These two categories have different owners (admin vs user) and different storage locations. The initial design placed both on the Plan, but further analysis showed that stop conditions are fundamentally per-template preferences.

## Decision

- **`boardType`** → stored in the Plan's `document` JSONB. Mandatory field.
- **`stopWhen`**, **`catchUpThreshold`**, **`maxPages`**, **`olderThanDays`** → stored in the SourceTemplate. A new JSONB config column or dedicated columns on the `source_templates` table.

## Alternatives Considered

### All fields on Plan

- **Description**: Both board type and stop conditions live on the Plan document.
- **Pros**: Single source of truth, simpler schema.
- **Cons**: Cannot vary stop behavior per user; first-run detection requires per-template context.
- **Why rejected**: Stop conditions are user preferences, not board characteristics. First-run detection (`totalRuns`) is inherently per-template.

### All fields on SourceTemplate

- **Description**: Even board type moves to the SourceTemplate.
- **Pros**: Fully user-controlled.
- **Cons**: Board type is not a user choice — it is a fact about the board. Duplicating it per template adds no value.

## Consequences

### Positive

- Clear ownership: admin owns board type, user owns stop behavior
- First-run detection naturally works at the template level
- Users can have different stop strategies for the same board

### Negative

- Extension must read from two sources (plan for boardType, source run/template for stop config)
- SourceTemplate needs a schema change (new JSONB config column or dedicated columns)

### Risks

- Extension currently receives only `{ runId, surfaceUrl, planId }` per source run. Stop config must be added to the execution message or queried separately. **Mitigation**: add stop config fields to the SourceRun GraphQL query response, populated from the template at query time.

## Implementation Notes

- Plan: `boardType` is mandatory in `PlanSchema` Zod validation.
- SourceTemplate: add a `config` JSONB column to `source_templates` table, or add individual columns. JSONB is recommended for flexibility.
- SourceRun query: add stop config fields to `SourceRunType` so the extension receives them with each run.
- Extension: `CollectJobsService` reads `boardType` from plan, `stopWhen` from run config.
