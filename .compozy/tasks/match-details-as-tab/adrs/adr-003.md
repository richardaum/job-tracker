# ADR-003: SSE Ownership in MatchTabContent

## Status

Accepted

## Date

2026-05-23

## Context

The standalone `MatchAnalysisPage` uses `useEventSource` to listen for `match_status_changed` SSE events and trigger a refetch when match generation completes or fails. When match content moves into a tab, the SSE listener needs a new home. Two placements were considered: the `JobDetailsPage` view-model (which already manages `summary_status_changed` and `fill_status_changed`), or the `MatchTabContent` component itself.

## Decision

**The `useEventSource` for match status lives inside `MatchTabContent`**, not in the parent `JobDetailsPage`. The tab component manages its own SSE subscription, subscribes when the tab mounts, and cleans up when unmounted.

## Alternatives Considered

### Alternative 1: SSE in JobDetailsPage view-model

- **Description**: Add match SSE to `useJobDetailsViewModel`, alongside existing `summary_status_changed` and `fill_status_changed` listeners.
- **Pros**: Single SSE endpoint (`/jobs/:id/stream`) already used for summary/fill. No additional connection.
- **Cons**: Match SSE endpoint is `/matches/:id/stream` — different URL, different event name. Adding it to the job view-model couples match concerns into the job orchestrator. The match tab may not even be active (user on Overview tab), yet the listener would be running.
- **Why rejected**: The match SSE endpoint is `/matches/:id/stream` (not the job stream). Consolidating SSE URLs is out of scope. Running the listener when the tab is not visible wastes resources.

### Alternative 2: SSE in both JobDetailsPage and MatchTabContent

- **Description**: `JobDetailsPage` listens for match status to invalidate `job.match` in cache; `MatchTabContent` listens for its own refetch.
- **Pros**: Maximum cache consistency.
- **Cons**: Two SSE connections for the same event. Premature optimization. No demonstrated cache consistency problem with the simpler approach.
- **Why rejected**: Over-engineered. The simpler single-listener approach handles the core use case (user on Match tab during generation).

## Consequences

### Positive

- Self-contained `MatchTabContent` — no prop-drilling of SSE callbacks
- SSE subscription lifecycle matches component lifecycle (mount → subscribe, unmount → cleanup)
- No wasted SSE connection when user never opens the Match tab

### Negative

- If user generates a match from the Match tab and immediately navigates to Overview before SSE fires, the `MatchAnalysisField` in Overview won't auto-refresh. **Mitigation**: the `MatchAnalysisField` renders from `job.match` in the parent cache, which was populated when generation completed and the match was created server-side. The parent query uses `cache-and-network`, so navigating back will show fresh data.

### Risks

- Low risk: race condition where SSE fires after unmount (user navigated away). Mitigation: `useEventSource` already handles cleanup — the `EventSource.close()` in the cleanup effect prevents callbacks after unmount.

## Implementation Notes

- SSE URL: `${getApiBaseUrl()}/matches/${matchId}/stream`
- Event name: `"match_status_changed"`
- On `COMPLETED` or `FAILED`: call `refetch()` from `useJobMatchQuery`
- The `matchId` is derived from the `useJobMatchQuery` result (not from job.match, to keep independence)
