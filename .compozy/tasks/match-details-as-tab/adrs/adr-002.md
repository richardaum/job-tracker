# ADR-002: Independent Data Fetching for MatchTabContent

## Status

Accepted

## Date

2026-05-23

## Context

The `JobDetailsPage` already loads `job.match` via `useJobQuery` (which feeds the `MatchAnalysisField` summary in Overview). The new `MatchTabContent` component needs its own match data for the full analysis view (masonry grid, filters, verdict counts). Two approaches were possible: reuse the parent's `job.match` from cache, or run a dedicated query.

## Decision

**MatchTabContent uses its own `useJobMatchQuery(jobId)` query**, independent of the parent `JobDetailsPage` query. This gives the tab its own `fetchPolicy`, isolated SSE-triggered refetch, and avoids coupling its loading/error states to the job detail query lifecycle.

## Alternatives Considered

### Alternative 1: Reuse `job.match` from parent cache

- **Description**: MatchTabContent reads `job.match` from the Apollo cache populated by `useJobQuery` in `JobDetailsPage`.
- **Pros**: Zero additional network requests. Simpler component props.
- **Cons**: Couples tab rendering to parent query completion. SSE refetch of match data requires refetching the entire `Job` query. Loading/error states for match become entangled with job loading/error.
- **Why rejected**: The match analysis is a heavy payload (items array); lazy-loading it only when the tab is active is better for performance. Independent query also makes SSE refetch more surgical.

### Alternative 2: Hybrid — initial data from parent, background query

- **Description**: Use `job.match` as initial display data while running `useJobMatchQuery` with `fetchPolicy: "cache-and-network"` for updates.
- **Pros**: Perceived instant render when parent already has data.
- **Cons**: Adds complexity (dual data source, two sources of truth). Match data rarely changes except via generation — the first load will almost always be a fresh fetch.
- **Why rejected**: Unnecessary complexity for negligible UX gain. The match tab is not the default tab, so there is no pressure for instant render.

## Consequences

### Positive

- Decoupled loading/error/empty states between job detail and match tab
- Isolated SSE refetch — only `useJobMatchQuery` refetches, not the entire `Job` query
- Lazy loading: match data fetched only when user activates the Match tab
- Cleaner component contract: `MatchTabContent` receives only `jobId` as prop

### Negative

- Two queries for the same entity (job detail + match tab) sit in the Apollo cache simultaneously — minimal waste, same data
- `MatchAnalysisField` in Overview uses parent's `job.match` while Match tab uses its own query; slight risk of temporary inconsistency if one refetches and the other doesn't. Mitigated by both using `cache-and-network` and the SSE listener triggering refetch on the active tab.

### Risks

- Low risk: Apollo cache may briefly show stale match data if the user generated a match on one tab and switched to another. Mitigation: SSR handles initial load; `cache-and-network` handles navigation.

## Implementation Notes

- `MatchTabContent` props: `{ jobId: string }`
- Uses `useJobMatchQuery({ variables: { jobId }, fetchPolicy: "cache-and-network" })`
- SSE `useEventSource` lives inside `MatchTabContent`, triggers `refetch` on `COMPLETED`/`FAILED` status changes
