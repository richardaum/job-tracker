# ADR-004: Full Removal of Standalone Match Routes and Pages

## Status

Accepted

## Date

2026-05-23

## Context

The PRD calls for removing the `/matches` list route and the `/matches/[id]` detail route, replacing them with a Match tab inside `/jobs/[id]`. The standalone `MatchAnalysisPage` component contains ~360 lines of logic (query, SSE, filters, masonry grid, empty states, delete dialog, wizard, prefs dialog). Two strategies exist: extract reusable logic into `MatchTabContent` first, then delete the old code; or delete everything and build `MatchTabContent` from scratch referencing the old code.

## Decision

**Delete all standalone match route files and page components outright.** Build `MatchTabContent` as a new component that implements the same feature set. Keep shared sub-components (`MatchItemCard`, `MatchWizardDialog`, `MatchStatusBadge`, `MatchClassification`) since they are used by both the tab and existing code.

## Alternatives Considered

### Alternative 1: Gradual extraction (extract then delete)

- **Description**: Create `MatchTabContent` by extracting logic from `MatchAnalysisPage`, keep both alive during transition, then delete old files.
- **Pros**: Lower risk of missing functionality. Both can coexist for testing.
- **Cons**: Twice the work — extract, verify, then delete. Creates temporary coupling. `MatchAnalysisPage` has its own routing/page structure that doesn't map 1:1 to a tab component.
- **Why rejected**: The page structure (header, BackToLink, page-level error/not-found states) is not reusable for a tab. The reusable parts (filters, grid, cards, SSE, wizard) are already well-scoped and can be re-implemented cleanly in a tab component.

### Alternative 2: Keep old code as reference, don't delete

- **Description**: Remove routes but keep page components in the codebase as implementation reference.
- **Pros**: Reference material.
- **Cons**: Dead code in the repo. Confusion about which component is canonical. Import analysis tools (knip) will flag them.
- **Why rejected**: The codebase already has the version history in git. Dead code violates the project's dead code policy.

## Consequences

### Positive

- Clean removal: zero dead code, no import confusion
- Smaller surface area for future changes
- `MatchTabContent` can be designed specifically for the tab context (no page-level concerns)

### Negative

- Items to delete: `apps/web/src/app/(authenticated)/matches/page.tsx`, `apps/web/src/app/(authenticated)/matches/[id]/page.tsx`, `apps/web/src/modules/match-analyses/details/page/MatchAnalysisPage.tsx`, `apps/web/src/modules/match-analyses/list/page/MatchAnalysesPage.tsx` (and any associated barrel exports)
- Must verify all imports of deleted modules are cleaned up

### Risks

- Medium risk: some import may reference a deleted module that was not obvious from the file tree. **Mitigation**: run `pnpm typecheck` and `pnpm lint` after deletion; let the compiler find broken imports.
- Must confirm `MatchWizardDialog` and `MatchItemCard` don't import from deleted files.
