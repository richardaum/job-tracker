# ADR-002: Tab Subpages with Shared Layout

**Status:** Accepted
**Date:** 2026-05-23

## Context

The PRD defines 4 profile tabs (Identity, Settings, Resumes, Work Preferences) as subpages:
`/profile`, `/profile/settings`, `/profile/resumes`, `/profile/preferences`.
Each must share a common header (BackToLink + Heading + TabsList) while rendering its own content.

The codebase has two existing patterns: `<Tabs>` + `<TabsContent>` (CompanyDetailsPage) and `<Tabs>` with conditional rendering (MatchAnalysisPage). Neither uses App Router subpage routing — both render everything on a single page.

## Decision

**Use a shared `layout.tsx` at `/profile/layout.tsx` with individual `page.tsx` files per tab.**

The layout renders the common shell (BackToLink, Heading, TabsList). Each tab is a separate route segment with its own `page.tsx`. The TabsList uses `usePathname()` to determine the active tab based on the current URL pathname.

Navigation between tabs is Next.js client-side navigation via `<Link>` or the Tabs `onValueChange` pushing to the router.

## Alternatives Considered

### B — Single page with Tabs + TabsContent

All content in `/profile/page.tsx`. Cleaner component tree but no URL-based state, losing deep links and browser back/forward between tabs. Rejected because the PRD explicitly requires subpages.

### C — Search params (`?tab=settings`)

Simpler directory structure (one `page.tsx`), but fragile state management on back/forward navigation and harder to type-safely link to specific tabs. Rejected in favor of clean URL segments.

## Consequences

- **Positive:** Clean URL structure. Deep links work (`/profile/resumes`). Browser back/forward between tabs. Each tab page is independently lazy-loadable.
- **Negative:** More files created (6+ new route segments). The TabsList must maintain sync with the URL, which is a known React/Next.js integration point.
- **Neutral:** Follows Next.js App Router conventions for nested layouts.
