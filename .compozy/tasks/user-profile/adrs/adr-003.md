# ADR-003: User Settings as Typed Entity

**Status:** Accepted
**Date:** 2026-05-23

## Context

The profile's Settings tab requires persisting three user preferences server-side:

| Setting                    | Type           | Default |
| -------------------------- | -------------- | ------- |
| Auto-fill enabled          | Boolean        | false   |
| Auto-summary enabled       | Boolean        | false   |
| Duplicate detection window | Integer (days) | 30      |

There is no existing settings infrastructure. Spec 031 proposed a generic key-value JSONB table (`user_settings` with `userId`, `key`, `value`). The API currently hardcodes `APPLICATION_DUPLICATE_PAIRING_WINDOW_MS` as a constant (30 days in ms).

## Decision

**Create a typed `UserSetting` entity with explicit typed columns instead of a generic JSONB key-value store.**

```ts
@Entity("user_settings")
export class UserSetting {
  @PrimaryColumn("text") userId: string;
  @Column("boolean", { default: false }) autoFillEnabled: boolean;
  @Column("boolean", { default: false }) autoSummaryEnabled: boolean;
  @Column("int", { default: 30 }) duplicateWindowDays: number;
  @OneToOne(() => User) user: User;
}
```

A single mutation `updateSettings(input: UpdateSettingsInput!)` with all three fields (all optional for partial updates) replaces the generic `updateSetting(key, value)` pattern from spec 031.

## Alternatives Considered

### A — Columns on users table

Adding `autoFillEnabled`, `autoSummaryEnabled`, `duplicateWindowDays` directly to the `User` entity. Rejected because it couples application preferences to the auth identity entity, which already has 7 columns and would grow unbounded with future settings.

### B — Key-value JSONB table

A generic `UserSetting` table with `(userId, key, value JSONB)`. Rejected because:

- Loses type safety — consumers cast `value` at every access point.
- No database-level constraints on valid keys.
- Harder to query specific settings in SQL.
- Overengineered for 3 settings with known types.

## Consequences

- **Positive:** Type-safe access from NestJS services. Database constraints on column types. Single-row per user — no joins needed to fetch all settings. Migration is a straightforward `CREATE TABLE` + FK to `users`.
- **Negative:** Adding a new setting requires a migration (new column) and changes to the entity, input type, and GraphQL type. The generic approach would only need a data entry. This trade-off is acceptable given the low frequency of new settings.
- **Neutral:** The `duplicateWindowDays` hardcoded constant in `job-duplicate.constants.ts` must be replaced with a service call to read from `UserSetting`.
